# 他のツールとの違いと、なぜ今 Tsugumi なのか

計算やデータ処理を進めるとき、すでに多くの優れたツールやアプローチが存在します。
Tsugumi は、それらの良さを踏まえたうえで、これまでどうしても埋まらなかった空白を埋めるために設計されました。

## 既存の優れたアプローチと、それぞれの空白

- **対話型ノートブック（Jupyter / Google Colab / Marimo など）**
  コードを書き、すぐ下で結果やグラフを確かめる軽快さにおいて、ノートブックは非常に優れた環境です。近年では Marimo のように、セルの依存関係をグラフとして扱い、実行順序による状態の不整合を防ぐ試みも進んでいます。
  一方で、ノートブックは基本的に一つの言語・一つのプロセス空間の中で進みます。AI にセルを書き換えさせると前の試行が上書きされて消えやすく、「ステップごとに Nix で実行環境を分ける」「C++ と Python を同じ型契約でつなぐ」「過去のすべての実行の入出力をそのまま残して比較する」といった用途には向いていません。

- **コーディングエージェント・自律型 AI 研究（Claude Code など）**
  自然言語で意図を伝えれば、ファイルを探し、コードを書き、実験スクリプトを回してレポートまでまとめてくれます。試行錯誤を前に進める推進力は圧倒的です。
  しかし、対話とファイルツリーの上で処理が進むため、試行が大きくなるほど「どのデータに何をしてその結論に至ったのか」という全体の構造が人間の目から見えにくくなります。「途中のあの段階だけ条件を変えてもう一度確かめたい」と思ったとき、どこに手を入れるべきかを探し直す負荷が生まれます。

- **科学ワークフローエンジン（Snakemake / Nextflow / DVC など）**
  パイプラインの依存関係と実行環境を定義し、大規模な計算を再現性高く実行する仕組みとして非常に成熟しています。
  ただし、これらは基本的に「やるべき処理が固まったあとに、コマンドラインと設定ファイルでパイプラインを記述・運用する」ための道具です。まだ方針が固まっていない段階で、出力を目で見ながらその場で処理を組み替えていくような、探索的な試行錯誤の場としては距離があります。

- **GUI ノードツール（KNIME / n8n など）**
  箱（ノード）を線でつなぎ、処理の全体像を画面上で見渡せるのが大きな魅力です。n8n は SaaS や外部 API をつなぐ業務自動化に、KNIME はノーコード／ローコードでの表データ分析や機械学習に、それぞれ強い実績を持っています。
  ただ、これらは「あらかじめ用意されたノードを組み合わせる」か「ホスト環境の簡易スクリプトを呼ぶ」設計であり、自分や AI が書いた本格的な計算コードを環境ごと固定し、型と履歴を厳密に残して検証する用途は想定していません。

## なぜ「今」、この設計なのか

これまで、研究や開発の環境には解けないトレードオフがありました。

**「軽快に試行錯誤できること」**と、**「環境・型・記録まで厳密に保ち、全体の構造を見渡せること」**は、どちらかを選べばどちらかを諦めざるを得なかったのです。

たとえば、小さな処理ごとに Nix で環境を宣言し、FlatBuffers で入出力の型スキーマを定義し、C++ を共有ライブラリとしてビルドしてサンドボックス内で動かす。そうすれば再現性も安全性も実行速度も極めて高くなります。
しかし従来は、その**「厳密さのための手間」をすべて人間が手で支払わなければなりませんでした**。試行錯誤のたびに環境定義やスキーマを書くのは重すぎるため、探索の段階では環境や型が曖昧なまま進むしかなかったのです。

Claude をはじめとする AI がここまで賢く成熟した今、その前提が変わりました。

人間は Canvas 上で「どんな処理をして、どうつなぐか」という全体の構造（Draft）を描くだけでよい。これまでなら人間が面倒がって省略していた `default.nix` の環境宣言も、`_outputs.fbs` の型定義も、C++ や Python の実装も、AI が前後の文脈から組み立て、実際に動かして確かめることができます。

**「厳密さのコスト」を AI が引き受けられるようになったからこそ、人間は軽快な試行錯誤を手放さずに、再現性と見通しのよい実験基盤を手に入れられるようになった。**
そして逆に、AI が一気に大量のコードを書ける時代になったからこそ、人間側には「緩くて書きやすい場所」ではなく、**「AI が作った部品を、厳密な境界と構造の上で確かめられる足場」**が不可欠になっています。

それが、今 Tsugumi をこの形で設計した理由です。

---

以下では、この思想を支える Tsugumi の 8 つの仕組みを具体的に説明します。

## 1. 環境まで含めて再現できる（Nix）

ノートブックや一般的なノードツールのスクリプトは、原則としてそのマシンに入っている Python やライブラリを使って動きます。conda などで仮想環境を分けても、ライブラリの細かなバージョンやネイティブ依存はマシンごとに解決されるため、半年後に別の Mac で開くと結果が微妙に変わる、といったことが起こりえます。

Tsugumi では、**Card ごとに `default.nix` で実行環境を宣言**し、nixpkgs のリビジョンとハッシュまで厳密に固定します。

```nix
{ pkgs, inputs, params }: {
  run = inputs.tsugumi.cppCard { sdk = inputs.tsugumi.sdk { languages = [ "cpp" ]; }; src = ./src; };
}
```

- コンパイラ・インタプリタ・依存ライブラリのバージョンはすべて Nix のハッシュで一意に決まります。同じ定義であれば、どの Mac で動かしても同一のバイナリが使われます。
- Card ごとに環境が独立しているため、「この Card は古い NumPy、隣の Card は新しい NumPy」といった構成でも一切衝突しません。
- 評価には restricted eval と IFD（Import From Derivation）禁止を適用しており、宣言されていない外部ファイルやネットワークへ暗黙に依存する定義は書けません。
- 独自のキャッシュ機構ではなく Nix の derivation そのものでビルドの要否を判定するため、「古いキャッシュが残っていて結果が食い違う」という問題が起きません。

**「同じ入力・同じ定義なら、必ず同じ結果になる」ことをツールの仕組みとして徹底している**点が、Tsugumi の土台です。

## 2. 型のあるポート

ノード間を JSON や動的な変数で受け渡す仕組みは手軽ですが、「この処理に実際にどんな構造のデータが渡ってくるか」は動かしてみるまで分からないことが少なくありません。AI にコードを書かせる場面でも、前後のデータ構造が曖昧だと、キー名の食い違いや型の不一致が頻発します。

Tsugumi のポートは **FlatBuffers のスキーマによって静的に型付けされています**。

- 出力の型を `_outputs.fbs` で宣言すると、下流 Card の入力型は自動的に導出されます。合流（merge）では自動で union 型が生成されます。
- ポートをつないだ時点で構造的な互換性を検査するため、型の合わない配線は実行する前に検出できます。
- C++ では `input.number.value` のように、ポート名がそのまま型付きのメンバとして生成されます。文字列でキー名を引いてタイプミスに悩まされることがありません。
- 64 bit 整数・enum・struct・union・ファイル・ディレクトリを、C++ / Python / bash の間で一切の欠落なく受け渡せます（JSON を介した際に 64 bit 整数が浮動小数点に丸められて精度を失う、といった問題が起きません）。

## 3. 本格的なプログラムを高速に動かせる

Python でプロトタイプを作ったあと、計算の重い部分だけを C++ で書き直して高速化したい場面はよくあります。しかし既存のツールでは、C++ を組み込むために独自のバインディングを書いたり、毎回別プロセスとして起動してファイルを読み書きしたりする手間が必要でした。

Tsugumi は C++ を第一級の言語として扱います。

- C++ の Card は共有ライブラリ（`lib/main.so`）としてビルドされ、worker プロセスがメモリ上に読み込んで直接関数を呼び出します。呼び出しのたびにプロセスを起動したり、標準入出力のテキストへシリアライズし直したりするオーバーヘッドがありません。
- worker は実行をまたいで常駐し、メモリ上の状態を保持できます。また、次回使う worker を裏で先行起動しておくこともできます。
- 実測では、C++ Card 1 回の実行段階は平均 0.26 ms、Collatz デモの 1,344 回の呼び出し全体が 0.92〜1.0 秒で完了します（共通 VM 上、2 回目以降。[開発資料の計測](Development.md)）。
- Python・bash も同じ型契約の上で混在でき、「C++ と Python の独立した 2 つの実装に同じ入力を流し、結果が完全一致するかを 1 つのグラフ上で検証する」といった実験が自然に組めます（`collatz` デモ）。

## 4. 厳密な意味論を持つ制御フロー

分岐やループを含むパイプラインでは、「どの入力が揃ったら動くのか」「選ばれなかった経路はどう扱われるのか」が曖昧だと、再現性のない挙動につながります。Tsugumi は、制御フローを**スケジューラーの意味論として厳密に定義**しています。

- 入力の待ち合わせ方（`all`：全入力が揃ったら 1 値ずつ消費 / `any`：到着順に消費）と、有界キューによる背圧（バックプレッシャー）。
- 条件分岐（branch）で選ばれなかった経路の下流は `skipped`、未実装の Draft や上流の失敗に依存する経路は理由付きの `blocked` となり、それらと独立した経路は止まらずに最後まで進みます。
- フィードバックループは `maxRuns` で反復上限が保証され、意図しない無限ループで暴走しません。
- Card in Card（子 Workflow）は、外からは通常の Card と同じように配線・実行でき、内部だけを単体で再実行することもできます。
- さらに Nix の環境定義から「どの経路を通っても必ず先に実行される上流 Card」の定義を参照でき、その可否は分岐・合流・ループ・入れ子を考慮した静的解析によって判定されます。

## 5. すべての実行を記録し、途中からやり直せる

AI と試行錯誤を重ねるとき、一番困るのは「さっきうまくいったときのコードと入力がどれだったか分からなくなる」ことです。

Tsugumi は、**試行錯誤の履歴そのものを研究の記録として残す**ように設計されています。

- 呼び出しごとに、どの段階（評価・ビルド・実行・保存）に何ミリ秒かかり、キャッシュが使われたか、どの出力ポートへ値を送ったかをすべて記録します。
- 入出力の値は FlatBuffers のバイト列のまま、その時点のスキーマ（型定義）と紐づけて保存されます。後から Card の型定義を変更しても、過去の実行記録を正しく復元して読めます。
- 完了した実行履歴はプロジェクト内の `.tsugumi/runs.sqlite` にも書き出されるため、フォルダごとコピーしたり別の Mac へ移したりしても履歴がそのまま引き継がれます。
- 保持された成果物（ファイル・ディレクトリ）は改ざんを検出できます。
- 「前回保存された入力を使って、この Card だけを再実行する」「ここから下流だけを再実行する」ことができるため、途中の処理を手直ししながら検証を重ねる研究のサイクルに直結します。

## 6. Card ごとの強固なサンドボックス隔離

AI が生成したコードや外部から受け取った処理を自分の Mac 上でそのまま動かすことには、常にリスクが伴います。大事なデータを誤って書き換えたり、意図しない通信を行ったりする可能性があるためです。

Tsugumi の Card は、**Mac 本体から隔離された Linux VM の中で、さらに bubblewrap のサンドボックスに入れて**実行されます（詳細は [security.md](security.md)）。

- Card はデフォルトでネットワークも Linux capability も持たず、見えるファイルは読み取り専用の `/nix/store` と自身の入力・一時作業領域だけです。外部との通信や Mac 側フォルダへのアクセスは、設定（`network`・`hostFolders`、Experimental）で明示した Card にしか許されません。
- プロジェクトごとに専用の uid・名前空間・cgroup が分離されており、あるプロジェクトの Card が別プロジェクトのデータやプロセスを覗き見ることはできません。
- Mac 側から VM に共有されるのは、現在開いているプロジェクトのフォルダと、Card 定義やチャットで明示的に指定されたフォルダだけです。

そのため、AI が生成したコードも、Mac 本体の環境を汚したり危険にさらしたりすることなく安全に試せます。

## 7. 人が読めるテキストファイルとしての Workflow

GUI ツールの中には、ワークフローがデータベース内や巨大な単一 JSON / XML ファイルに保存され、Git で差分を追えないものも少なくありません。

Tsugumi のプロジェクトは**見通しのよい通常のフォルダ**です。

- `tsugumi.json`、`definitions/<Card>/_card.json`、`default.nix`、`src/*.cc`、`src/*.py`、`_outputs.fbs`、`layout.json` など、すべて人間がそのまま読めるテキストファイルで構成されています。
- 計算の定義（Card の処理や配線）と画面上の見た目（配置座標・付箋・グループ）はファイルが分離されているため、Git の差分から「計算ロジックが変わったのか、配置を整えただけなのか」が一目で分かります。
- 保存処理はジャーナル付きのトランザクションで行われ、万一途中で異常終了しても「全件適用」か「全件未適用」のどちらかにしかなりません。UI と Agent が同時に編集した場合もリビジョンで競合を検出し、互いの変更を黙って上書きしない仕組みになっています。

## 8. AI が「検証可能な部品」を作る

Tsugumi の Agent は、単にチャットでコードを教えてくれるアシスタントではなく、**人間による全体の設計と、AI による個別処理の実装・検証を分担する**ために作られています。

- 人間は Canvas 上に **Draft**（概要・処理内容・仮の入出力）を置いて先に配線し、パイプライン全体の骨格を描きます。
- 「Card を生成」を実行すると、Agent が Draft と前後の配線から入出力の型・Nix 環境・ソースコードを作成し、1 つのトランザクションとして保存したうえで実際に動かして検証します。途中で失敗したりキャンセルしたりした場合は、中途半端な変更を残しません。
- Agent が使うツールはすべて core の RPC 契約（FlatBuffers スキーマ）から自動生成されており、UI とまったく同じ検証ルールのもとで動作します。
- 生成されたコードも §6 のサンドボックス内で動くため、AI が書いたコードを安心して実行できます。
- なお、Workflow の実行自体に LLM は不要です。Agent を一切使わなくても、すべての作成・編集・実行は画面から完結します。

## まとめ

| 観点 | 対話型ノートブック | コーディングエージェント単体 | GUI ノードツール（n8n / KNIME 等） | Tsugumi |
| --- | --- | --- | --- | --- |
| 主な対象 | 対話的なコード実験・可視化 | 自然言語からのコード・スクリプト生成 | SaaS 連携 / ノーコード分析 | AI とともに作り、検証・再現する計算パイプライン |
| 構造の見通し | セルの並び（状態が暗黙になりやすい） | ファイルツリーとチャット履歴 | ノードと配線のグラフ | 型付きポートと階層を持つ Card のグラフ |
| 実行環境の固定 | マシンまたは単一の仮想環境 | ホスト環境または単一コンテナ | マシンのランタイム / conda | Card ごとに Nix で固定（ハッシュ単位） |
| ノード / ステップ間の型 | 動的（メモリ上の変数） | ファイルや標準入出力（規約次第） | JSON / 型付きの表 | FlatBuffers スキーマによる静的な型付き値 |
| C++ の扱い | 別途バインディングが必要 | ビルドスクリプトを都度作成 | 不可または限定的 | 第一級（共有ライブラリをメモリ上で直接呼び出し） |
| 実行の隔離 | 本体と同じ権限 | ホストまたはコンテナ単位 | 本体と同じ権限 | Linux VM + bubblewrap（Card ごとに隔離・通信なし） |
| 実行記録と再実行 | 直近のセル出力のみ | ログファイルや Git 履歴頼み | 実行ログ / ノード出力の保持 | 段階・値・型・成果物を全記録し、途中から再実行可能 |

この Tsugumi 自体も、Linux VM・Nix・C++ スケジューラ・FlatBuffers・WebGPU・SwiftUI にまたがる基盤を、Claude Code とともに短期間で作り上げたプロジェクトです。

AI が高度になり、複雑な実装を一瞬で引き受けられる時代になったからこそ、人間が問いを立て、過程を見渡し、自分の手で確かめ続けられるワークベンチが必要だと考えています。
