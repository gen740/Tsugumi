# Tsugumi Q&A

Tsugumi が解決したい課題と、そのために選んだ設計を Q&A で紹介します。操作の手順は[操作ガイド](usage.md)、実装の詳細は[主要機能](features.md)を参照してください。

## Q1. 既存の AI コーディングエージェントやノートブックと、何が違うのですか？

**人間が見て理解する処理の構造と、AI が編集し、実際に実行する対象が一致していることです。**

AI に解析を任せると、短時間で多くの試行が進みます。その過程を文章で受け取るだけでは、詳しい報告は長くなり、短い要約では途中の判断や試した条件が見えにくくなります。「この条件を変えたらどうなるか」と思うたびに AI に聞き返し、報告とコードを照らし合わせる負担も生まれます。

Tsugumi では、解析を Card とその接続からなる Workflow として扱います。AI はその構造を編集し、同じ構造が実行されます。人間も画面から Card を開き、入力・コード・結果を確認して、パラメータや処理の一部を変更できます。版のツリーと実行履歴を使えば、採用した手順だけでなく、失敗した試行や別の条件を試した枝もたどれます。

ここで残る試行過程は、採用した処理構造、コードの変更、実行の記録です。これらを直接確かめながら、次に何を試すかを人間が決められることを重視しています。

背景にある問題意識は[制作の背景](philosophy.md)、この仕組みを選んだ理由は[設計の独自性](novelty.md)にまとめています。

## Q2. なぜ自然言語だけでなく、Draft と Workflow で AI に指示するのですか？

**解析の流れそのものを、指示として共有するためです。**

「解析 A の結果を解析 B に渡す」という二段階の処理なら、文章でも容易に伝えられます。しかし、十段階の処理に分岐や合流が加わると、どの出力をどの入力へ渡すかを文章だけで書き続けるのは大変です。書いている人自身も、接続の抜けや食い違いを見落としやすくなります。

Draft は、名前と処理の内容だけを持つ、未実装の Card です。コードや型が決まる前に並べて線でつなげ（ポートは線に合わせて作られます）、そのフローチャートを仕様として AI に実装を依頼できます。実装後は出力型から下流の入力型が導出され、接続の整合性を確認して実行します。

処理の意図は言葉で、処理同士の関係は接続で表す。人間と AI が同じ箇所を指しながら、設計・実装・検証を進めるための仕組みです。

## Q3. 解析の再現性を、どのように確保するのですか？

**Nix で固定できる計算と環境をできるだけ固定し、実行時の処理には必要な自由度を持たせます。**

Tsugumi には、Nix が扱うビルドや依存関係の領域と、Card が動作する runtime の領域があります。Nix はコードと依存ライブラリから実行環境を構築します。プロジェクトの版とともに環境の定義を保持することで、別のマシンでも同じプログラムを同じ環境で動かすための基盤になります。

たとえば、長時間かかるシミュレーションを seed や条件を明示した Nix のビルドとして定義すれば、その出力を後続の解析に利用できます。後続の可視化や解析だけを変えた場合、シミュレーションの定義と依存関係が変わらず、その出力が Nix store に残っていれば再計算を省けます。

runtime は、ストリームの処理や状態を使った計算にも対応します。入力の到着順に処理する `any` モードや、起動の負担を減らす常駐 worker も、そのための仕組みです。worker の状態は実行をまたいで保持でき、実行ごとに初期化したい状態は `onRunStart` / `on_run_start` で扱えます。

同じ環境を構築できることと、あらゆる処理が必ず同じ結果を返すことは別です。乱数、外部データ、到着順、保持した状態に結果が依存する場合は、それぞれの計算で条件を定める必要があります。Tsugumi は、Nix による再現可能な基盤と runtime の自由度を組み合わせ、解析の流れをもう一度動かして検証できるように設計しています。

## Q4. なぜ、すべての実行データを保存しないのですか？

**大量のデータや連続した入力を扱う解析でも、必要な記録を選べるようにするためです。**

各 Card の全呼び出しについて入出力を無条件に残すと、短時間で再計算できる処理にも大量の保存領域を使うことになります。ストリームの可視化などでは、その負担が処理を繰り返し試す妨げにもなります。

そのため、入出力値を履歴に残す `recordIO` はデフォルトで `false` です。必要な Card で有効にし、ファイルなどの成果物を保持するかは `retainArtifact` で選びます。実行状態やログなどの記録と、全入出力値の保存は分けて扱っています。

また、**部分再実行に使う最新入力は、全呼び出しの入出力履歴とは別に保存します。** `recordIO` を無効にしていても、保存された最新入力を使って Card を試し直せます。

長期に固定して使いたい計算結果は Nix の出力として扱い、試行中に必要なデータは履歴や成果物として残す。解析の規模と目的に応じて記録を選びつつ、コード・環境・処理の流れを保つことを重視しています。

## Q5. 解析の途中からやり直せることには、どんな意味がありますか？

**AI と人間が、一段ずつ処理を作って確かめるためのものです。**

解析を組み立てている途中では、「この Card の処理だけを修正したい」「グラフの表示条件だけを変えたい」という場面が繰り返しあります。そのたびに上流からすべてを実行する必要があると、試行の往復が遅くなります。

Tsugumi では、保存された最新入力を使って選択した Card を実行したり、そこから下流へ処理を進めたりできます。子 Workflow を対象にして、その範囲を試すこともできます。分岐の 1 つから下流へ進めると、合流する Card は今回届かないポートに保存された入力を使い、他の分岐を実行し直さずに比べ直せます。必要な入力がまだ保存されていない場合は、まず上流を含む Workflow を実行します。

この操作は、現在作っている解析の一部を検証するためのものです。過去の呼び出しの入力だけを取り出しても、その時点のコードや上流の条件まで戻るわけではありません。また、上流を変更した後の部分実行では、保存済み入力が新しい上流の結果に更新されているとは限りません。合流する Card でも同じで、条件を変えただけでまだ実行していない分岐の値は、前の条件のままです（どの実行の値かは実行のジャーナルに残ります）。

部分実行で調整を進め、**最終的な結果を確かめるときには Workflow 全体を通して実行する**、という使い方を想定しています。その際も、Nix で固定した重い計算の出力は、再利用できる条件が揃っていれば使い回せます。

## Q6. Git と実行履歴は、それぞれ何を記録するのですか？

**Git は解析の定義を、実行履歴は動かしたときの記録を保持します。**

| 記録先 | 主に残すもの | 使い道 |
| --- | --- | --- |
| Git | Workflow の定義、コード、パラメータ、環境の定義など | 変更をたどり、過去の版から別の試行を始める |
| SQLite の実行履歴 | 実行状態、ログ、表示結果、設定に応じた入出力値など | 実際に何が動き、どんな結果になったかを確認する |

版管理が有効なプロジェクトでは、実行開始時に保存済みの内容を必要に応じて commit し、その実行に commit を関連づけます。同じ版で何度も実行できるので、一つの commit に複数の実行が対応します。終了時には Git notes に実行結果の要約を追記し、詳しい出力やログは実行履歴で扱います。

版のツリーから「この版から始める」を選ぶと、その版の内容に戻って試行を続けられます。過去の分岐点から別の方法を試しても、以前の流れを残せます。過去のコードへ戻る操作と、当時の runtime の状態や全データを復元する操作は区別しています。

解析を再び組み立てて動かす土台は、コードと定義です。実行履歴は、その解析で何が起きたかを読み解くために使います。詳しい操作と保存の仕組みは[版の管理](versions.md)を参照してください。

## 補足 Q. Nix の上流参照は、どのように検証するのですか？

`default.nix` では、必ず先に実行される上流 Card の定義を参照できます。参照できる範囲は、評価器に渡す `inputs.upstream` / `inputs.local` の内容で制限しています。同じプロジェクト内の、どの経路で発火しても必ず先に実行されるコード Card が対象で、`inputs.local` はさらに同じ階層の Card に限ります。

保存や検査の段階では、ソースに直接書かれた参照を軽量なスキャナで確認し、自分自身、存在しない Card、先行が保証されない Card への参照を早めに知らせます。コメントや文字列の本文は対象から外し、文字列中の式の埋め込みは確認します。

この事前チェックは、Nix 全体を評価するものではありません。別名や動的に組み立てた属性名など、静的に確認しない参照は Nix の評価時に扱います。そこで提供されていない上流属性を参照すれば、評価エラーになります。早期に分かりやすい診断を出す仕組みと、実際に参照可能な定義を渡す仕組みが、それぞれの役割を担っています。

詳細は[主要機能の上流定義の参照](features.md#上流定義の参照inputsupstream)を参照してください。
