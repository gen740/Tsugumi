# Development

Material for developers: Tsugumi's runtime, its design decisions, the test suites, performance measurements and implementation status.
Installing and building the app are in [INSTALL.md](../INSTALL.md), the pinned versions of dependencies in [Lock.md](Lock.md), and the overview for users in the [README](../README.md).
File paths and commands on this page are relative to the root of the repository.
What exists now is in [Implementation status](#implementation-status), and how it is checked in [What has been checked](#what-has-been-checked). Measurements are records at the date and setup in their heading (measurements of earlier setups, and records of bugs, are in the Git history).

## The runtime

The types of ports check that wiring is consistent, and Nix pins each Card's environment by hash.
The run history and artifacts are persisted, and each Card's input and output values are recorded as configured.

In the macOS app, computation runs in an isolated Linux VM on the Mac, and Cards' access to the outside network is off by default. The Web UI uses the same VM on a Mac when started with the `tsugumi` command; started from the repository, it uses `tsugumid` directly on the Mac and isolates Cards with Seatbelt ([where the Web UI runs](WebUI.md)).
On the other hand, the Agent, which uses an outside LLM, is sent the conversation and what its tools read (source code, logs, input and output values and so on), so the isolation of the computing environment and the extent of data sent to outside models must be managed as separate things. The details are in [Security and isolation](security.md#what-is-sent-to-the-model).

The graph execution engine supports conditional branches (branch), merges (merge), bounded feedback loops and nested child Workflows (Card in Card).
In the macOS app, one shared Linux VM for the whole app (using `Virtualization.framework` directly) runs a separate `tsugumid` process for each open project.
A main window shows one project, and several windows can be open at once ([Several projects](features.md#several-projects)). The Web UI has one per browser tab.
The SwiftUI app and the Agent on macOS are equal clients that both talk to `tsugumid` through the same FlatBuffers RPC contract.

```text
Shared VM (one per app, Virtualization.framework)                 macOS
 tsugumi-vmd (vsock: control 1024 / RPC 1025)
 nix-daemon ── shared /nix/store (store disk)
 project A: tsugumid (own uid, mount/PID namespaces, cgroup) ── vsock ─ 127.0.0.1 relay ── SwiftUI UI (+ Dawn rendering)
   ├ document, journal, receipts (/project = virtiofs)                                  └ Agent (models, conversations, tools)
   ├ SQLite history, logs, artifacts                                   ── same RPC ──┘
   ├ scheduler, Nix evaluator (libnixexpr embedded in the process)
   └ worker pool (resident across runs and standby workers, isolated with bubblewrap)
 project B: tsugumid (likewise; stopping A does not affect B)
```

## Main design decisions

- **JSON goes through typed schemas** (hosq). A document is validated whole with `json::GenericDom` (UTF-8, duplicate keys, non-finite numbers) before being decoded into structs, and unknown keys are refused. hosq cannot encode with per-member omission, so **the canonical form of a document file is the validated text received from the client itself**. The core never re-encodes documents, so the original notation of integers (64-bit included) is kept and passed on as it is. JSON internal to the core (journal, view, job and so on) is encoded as structs with all fields required.
- **Saving**: a change is applied provisionally to the document model and validated → the journal (with the contents of all files and the receipt) is fsynced → files are replaced atomically → the commit is recorded. A crash in the middle is reapplied from the journal at startup, so the result is always all applied or none (with fault-injection tests).
- **Saving during a run**: a save that changes the computation's definition (its execution fingerprint) is refused with `busy` while running; layout changes and the like are accepted (so as not to stop drags).
- **pkgsPath**: `tsugumi:default` (the bundled pin) or `https://github.com/NixOS/nixpkgs/archive/<rev>.tar.gz#sha256-…`. Cards' Nix evaluation uses restricted eval, forbids IFD and limits allowed-uris.
- **Ports of built-in Cards**: trigger `out` / input (builds each message of `_outputs.fbs` from params of the same names; for File, copies the chosen project file into the run) / fork `in` → params `branches` / branch `value`, `condition` (value:bool) → `a`, `b` / merge declared inputs → `out` (a union named by input port, `tsugumi.merge.Merged`) / logger `in` / subgraph `boundary`.
- **Isolation**: the VM is given only the open projects, their control folders and the specified Mac folders; inside the VM each project has its own uid, namespaces and cgroup, and Cards run under bubblewrap (Seatbelt for a tsugumid on the Mac). Each route is described in §2–§4 of [Security and isolation](security.md).
- **Where persistent data and the runtime live**
  - **The data's location**: `~/Library/Application Support/Tsugumi/` (another folder for the development version; [development and release versions](#releases). `TSUGUMI_SUPPORT_DIR` can move just the VM and the store elsewhere).
  - **What `vm/` holds**: where the VM's boot disk is unpacked (`image/`, an APFS clone of the one bundled with the app), Tsugumi's source given to the VM read-only (`source/`, what `macOS/Container/vm-source.txt` lists, copied at each boot), the sparse disk image of the Nix store shared by all projects, `store.img` (up to 64 GiB by default, only what is used), and console logs (`console.log`, the previous `console.prev.log`, and the app's own record `launcher.log`). Each project's control folder is in `environments/<id>/control/`.
  - **The store**: the VM mounts the store disk as `/persist`, and `/nix` is an overlay of the rootfs's store (lower) and `/persist` (upper); all projects use one nix-daemon.
  - **Building Tsugumi itself**: tsugumid, tsugumi-vmd, the terminal's tools and the formatters are built by the VM's `/init` with Nix inside the VM from the shared source's flake (`packages.<system>.vm-system`), and started. Dependencies come from cache.nixos.org, and tsugumid is compiled from source. The result is recorded per hash of the source's content in `/persist/system/<hash>` and made a GC root, so it is rebuilt only the first time and when the source changes (an app update, or changes to the core during development). Nothing is downloaded on the Mac side.
  - **Updating the boot disk**: when it has changed (an app update), the store is checked once (`nix-store --verify --repair`). Paths of the previous boot disk that are now gone are fetched again from cache.nixos.org if something (a Card's build, say) refers to them, and removed from the database if nothing does.
  - **GC roots**: each project's build results are `/nix/var/nix/gcroots/tsugumi/projects/<id>/<Card>--<result>` (the folder is created by vmd as root, and its parent is not writable from projects, so another project cannot claim it first). Each time a result is used, a temporary root (held by the daemon connection) and then a permanent root are taken, so checking validity and using it never race with GC. The last two results per Card are kept; roots unused for 30 days, and the root folders of projects not started for 30 days, are collected.
  - **Cleaning and resetting**: "Delete the build cache" in the project's settings only removes that project's roots; cleaning the shared store (deleting what has no root, vmd's `gc`) happens only with "Clean shared store" in the app's settings. With `keep-outputs = true`, the compilers and nixpkgs sources used to build rooted Cards survive cleaning. "Reset all environments" in the settings stops the VM and deletes `vm/` and `environments/` (and any environments an earlier version made in Apple container), without touching the run-history disk `vm/history.img`, the projects' documents and artifacts, or the host's `/nix/store`.
- **Where the run history lives**
  - **Primary copy**: the history's SQLite (runs, invocations, states, values, logs, displays, receipts) is `<id>/history.sqlite` on the VM's run-history disk (`vm/history.img`, sparse, up to 32 GiB, mounted at `/history-disk`), visible only to that project's tsugumid as `/history` (`--history-dir`; without it, `.tsugumi/history.sqlite`). Waiting for each commit between Cards no longer goes through a shared folder.
  - **The disk's settings**: kept apart from the store disk (`synchronizationMode: .full`, F_FULLFSYNC on the Mac at every commit) and attached with `.fsync` (records already committed survive the app or the VM crashing; on a power loss of the Mac, the last writes may be lost; judging by the speed of synchronous writes to a shared folder, estimated to be about the same as when it was on the shared folder). It can be reset separately from the store, and survives "Reset all environments".
  - **The copy in the project**: with "Save run history in the project" in the Workflow's settings on (`saveRunHistory` in `tsugumi.json`, default true), finished runs are also appended to `.tsugumi/runs.sqlite` (when writing has paused for 2 seconds, at the latest after 30, and on exit; not counted in the run's time).
  - **The copy's format**: a fixed shape (`format = tsugumi-runs`, `version = 2` in `meta`). Values are kept as FlatBuffers bytes with their SHA-256, pointing at `schemas` (hash → bfbs and root type), so a reader can interpret them on the spot even if types changed between runs. Logs keep the fragments as written and their positions (preserving the order of the whole Run's log), and artifacts point at files in the project, `.tsugumi/runs/<run>/`. Running state, receipts and last inputs are not included.
  - **Carrying it along**: on opening, runs missing from the VM are imported, matched by `run_id`, so the history follows a project that was copied or moved to another Mac.
  - **Deleting**: "Delete Run History" (`RunHistoryDelete`; everything, or what finished before a given time; not while running) deletes from three places: the VM, `.tsugumi/runs.sqlite` and the per-run files. The history in the VM is not deleted automatically; under "Run history in the VM" in the app's settings you can see its size and also delete that of projects whose folders are gone (vmd's `histories` and `forget`).
- **Preventing double starts**: the VM is started only by the one app holding the flock on `vm/vm.lock` (a second app stops with "Another Tsugumi is using the runtime"). The core takes a non-blocking flock on `.tsugumi/tsugumid.lock`, and before opening the document also checks that a second flock on the same file is refused (that the location really enforces locks).
- **A Card's stages**: waiting for inputs → SDK preparation (generating the contract of inputs, outputs and params) → Nix evaluation (the evaluator embedded in tsugumid) → build (the daemon; nothing if the result is in the store) → run (`preRun → run → postRun`) → output validation → saving → done. For each invocation the core records the stages passed, with start and end times and results (done, cache used, reused as prepared in this Run, failed, stopped), in `InvocationSummary.stages`, and returns them in both notifications and the history. It also keeps whether the worker was reused (`worker_reused`), the output ports that actually sent values (`outputs_sent`; for a branch, only the chosen side) and when the inputs were complete (`ready_at`). The UI builds the stage display and the highlighting of wires from this record alone, never guessing from the final state. There is one deadline for the whole invocation, and cancellation and the deadline are checked before each stage starts. preRun / postRun run per invocation in its working directory even when the worker is reused, and receive none of the Card's inputs (preRun prepares; postRun handles artifacts and cleanup: `TSUGUMI_OUTPUT_DIR`, the output ports sent `TSUGUMI_OUTPUTS`, `TSUGUMI_FAILED`). preRun's environment variables and `cd` carry over to later stages, and postRun runs as cleanup even after a failure (`TSUGUMI_FAILED=1`; the earlier failure is not erased). After stopping or a deadline, nothing starts, postRun included.
- **The Card SDK**: `default.nix` makes the SDK from the contract, and the Card's body is written in `run`. If it is a derivation (package), the worker loads its `lib/main.so` and calls it in memory; if it is a string, it runs as bash (one or the other). The SDK generates and builds only the languages listed in `languages`, and the parts that do not depend on the contract (visualisation, context, logs and so on) are the common `libtsugumi_card.so`, built once per environment (what is made per Card is just the types and a thin adapter). inputs / outputs / params can also be passed explicitly to `sdk { languages = [ … ]; }`. Examples of `default.nix` and of each language's code are in [Your first Card](CardGuide.md) (which a test runs as it is) and [Features §3 and §4](features.md#3-reproducible-environments-with-nix).

  `Card::Input` has a member per input port (`std::optional` for optional inputs, a union named by input port for a merge), `Card::Output` has a `std::optional` per output port (only those set are sent), and `Card::params()` gives the params (numbers and bools are `flatbuffers::Optional`, which can represent unset, so read them with `.value()` / `.value_or(x)`). File / Directory are paths in `.value`, and the output location is `tsugumi::context().output_directory`. Fail with `throw tsugumi::Failure(kind, message)`, and check for stopping with `tsugumi::cancelled()`. Python has `main(ctx)` and an optional `on_run_start(ctx)`. A Card need not include generated headers (`_inputs_generated.h` and the like).
- **Workers**: the project's worker pool holds a worker per Card. A worker with `reuseWorker` (default true) stays resident across runs (static state included; `onRunStart` / `on_run_start` at the start of each run), and ends when build or run conditions change, on failure, cancellation or a deadline, when the project stops, after 10 minutes unused, above 2 GiB of memory, or as the oldest once more than 32 are resident. For a `reuseWorker = false` Card, the next fresh worker is started ahead each time it is used (the sandbox, starting the worker, loading `lib/main.so` and Python imports; preRun is per invocation). Loading happens in the worker's own `work/`. The body's environment variables are, from weakest to strongest: the values when the worker started, the invocation's values, values the Card set while loading (at the top of `main.py`; they last while resident), and preRun's exports; Python's `os.environ` is aligned to this per invocation too. Loading comes before preRun, so settings libraries read when loading (thread counts for OpenBLAS or libgomp, say) must be set at the top of `main.py`, before the imports. The SDK does not import `flatbuffers`, which loads numpy, first, so this is in time. Workers are started on a long-lived thread of the pool (bubblewrap's `--die-with-parent` stops the worker when the thread that started it ends). For `filesystem: false` Cards, `work` and `tmp`, and the files of preRun / bash's run / postRun, are in a per-worker temporary area inside the VM (not the project's shared folder), emptied between invocations. `out` is made only for Cards with File / Directory outputs, and kept for downstream and artifacts. From inside the sandbox, what is visible is the project's `runs` and saved inputs (read-only, bound once at start) and the worker's own temporary area; the invocation's output folder is passed as an FD with `SCM_RIGHTS` and shown as `/proc/self/fd/900`, and the core maps it back to its real path and validates it. The working folder is not passed as an FD (`getcwd` fails for a current folder pointing outside the sandbox). `filesystem: true` Cards also run in the temporary area, and `work` and `tmp` are copied into the run's folder after the invocation. Inputs are not passed as FDs because reopening through `/proc/self/fd/N` can break read-only (inputs are protected with read-only mounts). The Mac development environment (without bubblewrap) uses the real paths as they are.
- **bash inputs**: for each port `P`, `JSON_P` (the path of a JSON file, with no size limit; `jq` is available), and for File/Directory, `FILE_P`/`DIR_P`. The input JSON and its converter are made only when running a bash `run`. The output is the JSON in `$TSUGUMI_OUTPUT`, type-checked per port (separate from the artifact's `out`, so it works for Cards without artifacts).
- **Nix upstream references**: `default.nix` can refer with `inputs.upstream."<Card path>"` (`inputs.local.<id>` for the same level) to the attribute sets (`run`, `preRun`, the functions and values of `exports`, store context) of the code Cards that **always run first, whichever path fires it**. Several paths into the same port take the intersection, `all` the union of required inputs, `any` the intersection of all inputs, and loops a greatest fixed point; Cards on only one side of a branch, downstream Cards and the Card itself are not passed (the static diagnostics `nix_reference_*`). Only what is referred to is evaluated, lazily, and unchosen branches are not built. What Nix is given is the sources (except `_card.json` and `_meta.json`), the input types, the Nix params and the upstream definitions referred to; run-time-only params are not included. There is no Tsugumi-specific build key or cache record: if the result of the evaluated derivation (outPath) is in the store, nothing is built. There is one evaluator per tsugumid, reusing the loading of nixpkgs, the evaluation state and the daemon connection across Cards and runs (cancellation and `buildTimeoutSeconds` stop only the evaluator's thread).
- **Card in Card**: a child Workflow maps outer ports to inner Cards' ports with `boundary.inputs/outputs`, and from outside it is connected and run like an ordinary Card (it can be the target of a Run; run alone, it uses saved values at its boundary inputs). State and history are told apart by full Card path. It is a different thing from visual-only groups (layout.json).
- **Summaries**: a Card's summary is kept only in `description` of `_meta.json`, whatever its kind (Cards in Cards too; not in `_card.json`). `_meta.json` is not part of Nix evaluation, so rewriting it causes no rebuild.
- **Drafts**: `_meta.json` holds the summary, the processing, constraints, the conditions for completion and the purposes of inputs and outputs. Ports are made automatically when wires connect (inputs in `_card.json`, outputs in `_meta.json`; removed when the last wire is cut) and can be wired without types. A Draft never runs or counts as succeeded; Cards depending on a Draft are blocked with a reason, and independent parts run as usual. "Generate Cards" gives the Agent the Drafts, wires and descriptions, and has it save types, Nix and sources in one PutDefinition/PutSource transaction before validating and running (on failure or cancellation in the middle, nothing is saved and the plan stays). When an Agent's save (`origin` `agent`) turns a Draft into something other than a Draft, `Service::save` inspects `_meta.json` (`permissions::incomplete_draft_intents`, inside Cards in Cards too) and saves nothing, with `validation_failed`, if `description` is empty, if the Draft had a `description` or `content` but `context` is empty, or if the Draft's `description`, `content` or `context` changed. What the text says (adding nothing that was not written) is a promise of the prompt; what can be checked is only whether it is empty and whether it changed. A save that deletes the Draft and replaces it with a Card of another id is not covered, nor are people's saves.
- **The Agent**: the separate package `agent/`. Tool definitions are generated from `tsugumi.bfbs` (with the FBS doc comments), and tool arguments ⇄ FlatBuffers are converted with the same BFBS (64-bit as decimal strings). The Agent gives each tool call an op_id and persists it on the host side with the conversation and the tool trail. A change whose response was lost is confirmed with OperationGet, never blindly resent. PNGs and JPEGs in tool results (image displays in `run_record`, reading files and artifacts) are sent to the model as images, not as strings (`ToolImages.swift`; on the Web, `splitImages`). Partially read or oversized images are not sent, with a note instead, and if the provider does not accept images, the conversation is resent with its images removed. What is needed for Python, C++ and bash Cards is in the instructions, so the model starts writing without reading references. The list of the Python SDK's methods is made from the SDK's source by `agent/Shared/generate.py` and put into the instructions. `reference_read` returns, in one call, all the files of a Card's folder, or a list of the files under any other folder. The model's API keys are kept in the Keychain and never given to the core or workers. Cancellation stops the model's communication and unsent tools, but not runs already accepted.

## Releases

- **The version number** is only in `VERSION` (read by the core, Nix, CMake and the app). The stable release starts at v1.0.0, and compatibility is not kept during the 0.x versions before it ([AGENTS.md](../AGENTS.md)).
- **Making a release**: in a checkout of origin/main, `macOS/tools/release.sh 0.2.0` rewrites `VERSION`, commits it and pushes it to main with the tag `v0.2.0`. Without a checkout, `gh workflow run release.yml -f version=0.2.0` (Actions does the same). Either way the release workflow (`.github/workflows/release.yml`) builds the app and creates a GitHub Release, which installed releases find and update to automatically (`macOS/Sources/App/Model/Updater.swift`).
- **The `tsugumi` command**: the same workflow puts `cli/install.sh`, `cli/install.ps1`, and the `tsugumi-macos-arm64.tar.gz` and `tsugumi-linux.tar.gz` made by `cli/package-macos.sh` and `cli/package-linux.sh` (each with a `.sha256`) on the release. The scripts are attachments of the release rather than files on the documentation site: the site updates on every push to main, so it would show scripts for versions with no distributions yet, whereas as attachments the scripts and the distributions are always the same version and arrive as they are through `releases/latest/download/`. The Node.js version and checksums are in `cli/node-version.env`. To try it locally, pass a folder holding the distributions as `TSUGUMI_INSTALL_BASE=file://…`, and keep the VM apart with `TSUGUMI_SUPPORT_DIR`.
- **The VM's boot disk** (`vm-boot.nix` and the pinned nixpkgs): after changing it, publish it to [gen740/tsugumi-vm](https://github.com/gen740/tsugumi-vm) before releasing, with `macOS/Container/build-image.sh --vm` and `macOS/tools/publish-vm.sh` (which also publishes the list of licenses and the corresponding source with the disk). The runners cannot use Apple container, so the release build fails without a published disk.
- **Development and release versions** (`AppChannel.swift`): `build-app.sh` makes the development version by default (`Tsugumi Dev`, bundle id `app.tsugumi.Tsugumi.dev`, `TsugumiChannel` `dev` in `Info.plist`), and with `--release` the release (`Tsugumi`, `app.tsugumi.Tsugumi`, `release`). The support folder (VM, store, control folders, conversation history) is `~/Library/Application Support/Tsugumi-dev/` for the development version and `Tsugumi/` for the release, and user settings (UserDefaults) are separate per bundle id too. Checks and tests during development (UI scripts, smoke, `swift test`) use the development version, so they never touch the VM of the release you use. The Python tests' shared VM is `build/test-vm`.
- **Signing development builds**: by default both are signed ad hoc. With ad hoc signing, the designated requirement is the hash of that build's binary, so the login keychain treats every rebuild as a different app and shows a permission dialog (reading the API key, for example). The development version can be signed with a certificate in this Mac's keychain (Apple Development or the like) named in the environment variable `TSUGUMI_CODESIGN_IDENTITY`: `TSUGUMI_CODESIGN_IDENTITY="Apple Development" macOS/build-app.sh` (part of the certificate's name, or its SHA-1, as `codesign --sign` takes; list usable certificates with `security find-identity -v -p codesigning`). The designated requirement becomes the certificate and bundle id, unchanged across rebuilds. `--release` ignores the variable and stays ad hoc (release artifacts do not depend on the environment). The first time after switching from ad hoc, the keychain dialog appears once (choose "Always Allow", or save the key again); after that it does not. The `com.apple.security.virtualization` entitlement the VM needs is attached with either signature.
- **Automatic updates** happen only in releases. 20 seconds after launch and every six hours, the app reads `api.github.com/repos/gen740/Tsugumi/releases/latest`, and if a version newer than the current one (not a draft or pre-release) has `Tsugumi.zip` and `Tsugumi.zip.sha256`, downloads them into a temporary folder on the same volume as the app and checks the checksum, `codesign --verify --deep --strict`, the bundle id, `TsugumiChannel` and the version number. The replacement happens in `applicationWillTerminate` (after stopping the VM) with `FileManager.replaceItemAt`; for "Restart to Update", the new app is opened after waiting for this process to end. No checks happen while a UI script or smoke run is going.

## The documentation site

The documents read on [GitHub Pages](https://gen740.github.io/Tsugumi/) are generated from the Markdown in `docs/`. In the repository's settings, the Pages source is `/docs` on the `main` branch.

- **Generating**: `node docs/site/build.mjs` (using marked from `web/node_modules`) makes `docs/index.html` and `docs/pages/*.html`. They are never edited by hand. The list and its groups come from `docs/README.md`. To look while editing documents or figures, `node docs/site/serve.mjs` (http://localhost:4100/) regenerates on every change and refreshes the open page.
- **For AI**: the same generation makes a Markdown version of each page (`docs/pages/*.md`, and `docs/index.md` for the README, with links rewritten so they work on the site) and their guide, `docs/llms.txt` ([llms.txt](https://llmstxt.org/)). The HTML points to the Markdown with `rel="alternate"` and to `llms.txt` with `rel="describedby"`. Serving is static, so there is no switching on `Accept: text/markdown`.
- **Moving figures**: Canvas 2D in `docs/site/js/`. The app's "Learn about Tsugumi" shows the same pages in a `WKWebView` (`macOS/Sources/App/Explainer/ExplainerWindow.swift`; `build-app.sh` bundles the story pages and their material), so the text and the figures have this one source. The gallery on Home and the demo in "Your first Card" are `docs/site/player/` (which uses the Web UI's Cards as they are and replays records of real runs), regenerated with `node docs/site/player/build.mjs` (after changing the Canvas and Card code in `web/src`, `web/src/styles/`, `demos/` or `narration.json`, regenerate and commit `docs/site/js/player.js`, `player.css` and `player-data/`). The demo thumbnails on the Home of the app and of the Web UI draw the same data (`docs/site/player-data/`): the Web UI with the player itself (`web/src/ui/demoPlayer.tsx`), the app with its own Card and wire components (`macOS/Sources/App/Home/DemoThumbnail.swift`). Where figures go is written in `STORY` of `build.mjs` as part of a sentence, and generation fails if that sentence disappears.
- **Generated files are never edited by hand, and CI checks they were regenerated**: the document pages are made with `node docs/site/build.mjs` (`--check` looks for differences). `test_docs.py` checks that the generated files match the documents and that no unparsed `**` remains. The player (`docs/site/js/player.js`, `player.css`, `player-data/`) is made with `node docs/site/player/build.mjs` and checked with `node docs/site/player/build.mjs --check`, which needs `web/node_modules` and `web/src/gen`. CI's Web step runs this `--check`, so a PR that changed `web/src/model/canvasKit.ts` or the like and forgot to regenerate fails (generation is deterministic: the same input gives the same bytes).
- **Without JS**: the text is static HTML, so it can be read. With reduced motion, the figures follow the scroll and the parts that move by the clock stop.

## Measurements (2026-11-03)

After the speed-ups, on the shared VM.

> **About the Collatz demo.** "Collatz" in this section is the demo as it was when it had two languages, C++ and Python (1,344 invocations). Today's `collatz` has Julia and R too, with 2,685 invocations, and Cards in those two languages start a process per invocation, so resident workers do not help them and one Run takes minutes. The Collatz in `test_demos.py`, which runs in CI, is a copy with only C++ and Python and still takes seconds (`test_collatz_27` 4.9 s). `measure_stages.py collatz` measures the current demo, so it cannot be compared with the table below.

Conditions: MacBook Pro M3 Max (36 GB), macOS 27.2, shared VM with 8 vCPUs / 16 GiB, the Collatz demo (1,344 invocations). Measured with `tests/python/measure_stages.py collatz` (VM; `--host` for a tsugumid on the Mac) and the app's smoke mode (`TSUGUMI_SMOKE_RERUN=1`); the values are for runs already built, with workers reused.
Changes: fewer history writes, resident and standby workers, a temporary area inside the VM, no input conversion except for bash, the embedded evaluator, and a separate history disk. "Before" was measured the same day under the same conditions.

| Measure | Before | After | Reading |
| --- | --- | --- | --- |
| A Run's duration (shared VM, the current setup with the history on the run-history disk; runs 2–5) | 4.5–5.0 s | 0.92–1.0 s (first run 7.9 s) | One synchronous write 0.34 ms (`dd oflag=dsync`) |
| Same (when the history was still in the project) | 4.5–5.0 s | 2.6–2.9 s | Most of the rest was waiting for commits of the history SQLite on virtiofs |
| Same (experiment: the history on the store disk) | | 6.4–6.6 s | The store disk is `.full` (F_FULLFSYNC per commit), one synchronous write 9.9 ms (virtiofs 0.14 ms). Hence a separate history disk |
| Same (a tsugumid on the Mac, for reference) | 1.35 s | 0.43 s | |
| One hand-off (670 in series on the C++ side) | 6.5 ms | 3.9 ms (0.55 ms in an experiment with the history on a tmpfs inside the VM) | |
| The run stage of a C++ Card (mean) | 4.6 ms | 0.26 ms | Creating and deleting folders on the shared folder, and the input files, are gone |
| Preparation stages from the second run on (total of 9 Cards) | about 470 ms | 20 ms | Reusing the evaluator (median 2 ms of evaluation per Card), no `nix-store` start or file writes |
| The first run (first after opening the project) | 7.8 s | 9.4 s | Evaluation including loading nixpkgs (once per tsugumid) |
| tsugumid's memory | — | 29 MB → 121 MB (after evaluation) | The evaluator and nixpkgs' evaluated state. 9 resident workers total 89 MB |
| Cleaning the shared store | — | 1203 → 712 MiB | The compilers and nixpkgs sources of rooted Cards remain (`keep-outputs`) |

The saving stage's record closes just before the commit, so waiting for the commit appears outside the stages (between the end and the notification).

Before the speed-ups, under the same conditions, it took 20–60 ms from the core finishing to the app showing it (the core does not wait for the UI; the app applies 13,000 notifications in 262–325 batches), and 6.2–9.8 s from launching the app to it being usable (including starting the VM).

## What has been checked

What each method of checking covers. Permissions needed by the environment for automating the UI, and what is checked by eye, are kept apart from the implementation status.

| Method | What it covers |
| --- | --- |
| UI scripts and screenshots | Operating real windows through the app's own paths and capturing Cards, child Workflows, sources, the timeline and the guide. The published images and how to capture them are in the [README](../README.md) and [macOS/tools/screenshots](../macOS/tools/screenshots/README.md). This covers something different from end-to-end tests with real mouse clicks and drags |

| The Agent and ChatGPT | With the test model, branches such as authentication, cancellation and retries are checked automatically. A record with the real Claude API is in [Evidence](Evidence.md#a-run-with-the-real-claude-api); for fixes on the real ChatGPT plan, see the commits above |
| CI and the shared VM | What CI covers, and its commands, are in [ci.yml](../.github/workflows/ci.yml), and the results in [GitHub Actions](https://github.com/gen740/Tsugumi/actions/workflows/ci.yml). The same checks can be run locally with `tests/ci-local.sh` (on a Mac it runs the Linux job in a Docker container).
