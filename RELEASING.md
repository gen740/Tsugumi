# Releasing Tsugumi

Run commands from the repository root. Replace `<version>` with the numeric `major.minor.patch` to publish and `<number>` with its release-candidate number; choose an untagged version at least as high as the existing tags. Build instructions are in [Installing and building](docs/INSTALL.md#building-from-source).

- **The version number** comes from `VERSION` (read by the core, Nix, CMake and the app). Every tracked `tsugumi.json` records that number as `tsugumiVersion`.
- **Making a release**: in a clean checkout whose HEAD is origin/main, `nix run .#release -- <version>`. main takes changes only through pull requests, so when `VERSION` is not the version yet the script opens the pull request that updates `VERSION` and the `tsugumiVersion` field of every tracked `tsugumi.json` in the same commit, then stops; after that merges, run it again and it pushes the tag `v<version>`. Without a checkout, once `VERSION` on main is the version, `gh workflow run release.yml -f version=<version>` tags it in Actions. Either way the release workflow (`.github/workflows/release.yml`) builds the app and creates a GitHub Release, which installed releases find and update to automatically (`ui/macos/Sources/App/Model/Updater.swift`).
- **Making a release candidate**. Run `nix run .#release -- <version>-rc.<number>` from a checkout of origin/main. `VERSION` and the packaged app and command report the numeric `<version>`. The workflow publishes the suffixed tag as a GitHub prerelease. Download the app from the candidate's release page. Set `TSUGUMI_VERSION` to `<version>-rc.<number>` when running a CLI installer for the candidate. The app's automatic updater follows stable releases. The app needs a manual reinstall to switch to the stable release of the same numeric version. The `tsugumi update` command uses the latest stable release.
- **Kit templates**. Update the project manifests in [tsugumi-kit](https://github.com/gen740/tsugumi-kit) to the new `tsugumiVersion` and update the core's kit pin for the release.
- **Before tagging**, build the release once from a checkout that has nothing but what Git tracks: `git worktree add <folder> origin/main && cd <folder> && nix run .#guest-image && ui/macos/build-app.sh --release`. The release workflow starts from such a checkout, and a development checkout can hide what it lacks.
- **The `tsugumi` command**: the same workflow puts `cli/install.sh`, `cli/install.ps1`, and the `tsugumi-macos-arm64.tar.gz` and `tsugumi-linux.tar.gz` made by `cli/package-macos.sh` and `cli/package-linux.sh` (each with a `.sha256`) on the release. Publish the installers and distributions together so `releases/latest/download/` serves matching versions. To try it locally, pass a folder holding the distributions as `TSUGUMI_INSTALL_BASE=file://…`, and keep the VM apart with `TSUGUMI_SUPPORT_DIR`.
- **The release-built guest**: the workflow resolves one immutable revision, then `.github/workflows/vm-image.yml` builds `packages.aarch64-linux.vm` and the native test package on `ubuntu-24.04-arm`. It uploads one artifact named for the evaluated `vm-boot` identity, containing `tsugumi-vm.tar.gz`, `vm-manifest.json` and `SHA256SUMS`. The Mac job downloads that artifact directly, verifies identity, revision and checksums, and embeds the same single payload in the app and CLI. One final publication job attaches all guest and app assets to the app's release. There is no manual VM publication step. A local `--release` build requires a complete verified artifact for HEAD in `dist/tsugumi-vm`; it never silently downloads/builds another one.
- **Development guest builds**: `nix run .#guest-image` (`nix/guest-image.nix`) uses the shared Nix source fileset, evaluates the complete guest identity and checks it on every invocation. A matching local artifact is reused; otherwise authenticated `gh` downloads the artifact of the same identity from Actions (`gh auth login`), from any run whose image job uploaded it. With neither it stops and says so; it never builds by itself. `--build` builds locally: Nix on Linux (or `TSUGUMI_VM_NIX_BUILDERS`), an Apple container on a Mac, which takes much memory. Image identity includes Tsugumi's native sources and dependencies, so an old boot disk cannot satisfy a newer runtime definition. Card-result retention is unchanged.
- **Development and release versions** (`ui/macos/Sources/Launcher/AppChannel.swift`): `build-app.sh` makes the development version by default (`Tsugumi Dev`, bundle id `app.tsugumi.Tsugumi.dev`, `TsugumiChannel` `dev` in `Info.plist`), and with `--release` the release (`Tsugumi`, `app.tsugumi.Tsugumi`, `release`). The support folder (VM, store, control folders, conversation history) is `~/Library/Application Support/Tsugumi-dev/` for the development version and `Tsugumi/` for the release, and hostd's settings and credentials are separate under those support folders too; presentation preferences use each app's UserDefaults. Checks and tests during development (UI scripts, smoke, `swift test`) use the development version, so they never touch the VM of the release you use. The Python tests' shared VM is `build/test-vm`.
- **Signing development builds**: by default both are signed ad hoc. The development version can be signed with a certificate in this Mac's keychain (Apple Development or the like) named in the environment variable `TSUGUMI_CODESIGN_IDENTITY`: `TSUGUMI_CODESIGN_IDENTITY="Apple Development" ui/macos/build-app.sh` (part of the certificate's name, or its SHA-1, as `codesign --sign` takes; list usable certificates with `security find-identity -v -p codesigning`). This gives the app a stable designated requirement across rebuilds. `--release` ignores the variable and stays ad hoc (release artifacts do not depend on the environment). The `com.apple.security.virtualization` entitlement the VM needs is attached with either signature.
- **Updates** are checked and downloaded only when requested from the menu or Settings. A release reads `api.github.com/repos/gen740/Tsugumi/releases/latest` and checks the archive checksum, code signature, bundle ID, channel and version. **Restart to Update** installs the staged app after orderly runtime shutdown and reopens it after this process exits. Ordinary Quit does not install a staged download.
