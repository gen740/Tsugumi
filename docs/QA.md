この Q&A は、その 3 つに Tsugumi がどう答えるかを、問いごとに短くまとめたものです。各問いの最後の「確かめる場所」には、その答えを画面・デモ・テストで確かめる方法を並べました。操作の手順は[操作ガイド](Usage.md)、仕組みの詳細は[主要機能](features.md)にあります。

## Q1. 既存の AI コーディングエージェントやノートブックと、何が違うのですか？

**人が見て理解する図と、AI が編集するものと、実際に動くものが、同じ Workflow です。**

AI に解析を任せると、試行は速く進みます。けれど、その過程は文章の報告でしか受け取れません。詳しい報告は長くて読み切れず、短い要約では途中の判断や試した条件が消えます。報告とコードを照らし合わせるのも人の仕事です。

Tsugumi では、こうなります。

- 解析は、Card を線でつないだ Workflow です。AI が編集するのも、実行されるのも、この Workflow です。
- 気になった Card を開けば、入力・コード・結果がそこにあります。値やコードを変えて、その Card だけを動かし直せます。
- 採用した手順だけでなく、失敗した試行や別の条件を試した枝も、版のツリーに残ります。

AI の報告を読んで信じるのではなく、気になったところへ直接行って、自分で動かして確かめる。そのための形です。

**確かめる場所**

- 画面: デモ「Cas A · Chandra RGB」では、スペクトルの Card を見ると、緑の帯域（1.65–2.25 keV）が Si の輝線を含むことが分かります。画像の色が何を意味するのかを、同じ画面の Card で確かめられます（[README](../README.md#画面でたどる実験と検証)）。
- 画面: デモ「Data to report」のコピーで `aggregate` の `fail_on_purpose` を入れて実行すると、失敗した Card が下流を止め、その記録が Card に残ります。外して `aggregate` だけを実行し直せます。
- UI と Agent が同じ RPC を使う対等なクライアントであること: [protocol/tsugumi.fbs](../protocol/tsugumi.fbs)、[test_agent_contract.py](../tests/python/test_agent_contract.py)
- 背景: [AI に使われないために、何を作るか](Philosophy.md)、[設計の独自性](novelty.md)

## Q2. なぜ自然言語だけでなく、Draft と Workflow で AI に指示するのですか？

**処理のつながりは、文章よりも図のほうが正確に渡せるからです。**

観測データをダウンロードして、エネルギーで区切って、描画する。やりたいことは、紙に箱を三つ描けば伝わるくらい単純です。それなのに文章で頼むと、長い指示を書き、長いレポートを読み、伝わったかどうかを確かめ直すことになります。10 段の処理に分岐と合流が入れば、どの出力をどの入力へ渡すかを文章で書き切るのは、さらに難しくなります。書いた本人も、抜けや食い違いに気づけません。

- **Draft** は、名前と「何をするか」だけを書いた、まだ実装のない Card です。`E` で置いて書き、線でつなぐと、ポートは線に合わせてできます。
- 並べた Draft の図を仕様にして、右上の「Card を生成」で Agent に実装を頼みます。
- 実装後は、出力の型から下流の入力の型が決まり、配線の食い違いは実行前に診断として出ます。
- 1 つの出力から出せる線は 1 本です。1 つの値を複数の Card に送るときは fork Card を通すので、分配も図の上に Card として見えます。

処理の意図は言葉で、処理どうしの関係は線で書きます。人と AI が同じ箇所を指しながら、設計・実装・検証を進められます。

**確かめる場所**

- 画面: デモ一覧の「(Draft)」の付いたデモ（「Cas A · Chandra RGB (Draft)」など）は、実装前の Draft だけの Workflow です。コピーを開いて「Card を生成」を押すと、Agent が実装します（API キーか ChatGPT のプランが要ります）。
- Draft を実装する保存の規則（説明が空なら拒否する、Draft にあった内容は変えさせない）: [test_draft_intent.py](../tests/python/test_draft_intent.py)
- 実際の Claude API で、Draft から Card を作って実行・検証した記録（うまくいかなかった試行を含む）: [AgentRun.md](AgentRun.md)
- 型と配線の検査: [主要機能 §2](features.md)、[tests/cpp](../tests/cpp)

## Q3. 解析の再現性を、どのように確保するのですか？

**実行環境は Nix で固定し、結果を左右する条件は Card ごとに決めます。**

天体物理の解析ソフトウェア（NASA の [HEASOFT](https://heasarc.gsfc.nasa.gov/docs/software/lheasoft/) など）は長大で、同じ環境を作るだけでも一苦労です。作者が研究の中で行き着いた答えが Nix で、HEASOFT を Nix で使えるようにしたものも[公開しています](https://github.com/gen740/heasoft)（[出発点](Origin.md)）。Tsugumi は、その答えを Card 1 枚ずつに当てはめています。

- 各 Card の実行環境（言語のツールチェーンとライブラリ）は、その Card の `default.nix` から Nix が作ります。定義はプロジェクトの版と一緒に残るので、別のマシンでも同じ環境を作れます。
- 重い計算（長いシミュレーションなど）は、seed や条件を書いた Nix のビルドにできます。定義と依存が変わらなければ出力は Nix store から再利用されるので、後段の解析や可視化だけを何度でも試せます。
- ただし、同じ環境なら必ず同じ結果になる、というわけではありません。乱数・外部データ・到着順（`any` の Card）・常駐 worker が保持する状態に結果が依存するなら、その条件を Card で決めます。seed を params にする、実行ごとの初期化を `onRunStart` / `on_run_start` に書く、などです。

**確かめる場所**

- デモ「Cas A · Chandra RGB」: Chandra の観測を hash で固定して取得します。520 MB の観測は最初の実行で 1 度だけ取得され、2 回目以降は Nix store のファイルを使うので、Run 全体は 10 秒ほどで終わります（[README](../README.md#画面でたどる実験と検証)）。
- デモ「Collatz」: C++・Python・Julia・R で別々に書いた同じループが、27 から同じ 112 個の数列を返すことを確かめます（[test_demo_collatz.py](../tests/python/test_demo_collatz.py)）。
- Card の環境の定義: [sdk/nix/default.nix](../sdk/nix/default.nix)、[主要機能 §3](features.md)
- 常駐 worker と、実行ごとの初期化: [test_workers.py](../tests/python/test_workers.py)

## Q4. なぜ、すべての実行データを保存しないのですか？

**何を残すかを、Card ごとに選べるようにするためです。**

全呼び出しの入出力を無条件に残すと、ストリームやループの Card ではすぐに保存が膨らみ、試行そのものが重くなります。そこで、残すものを次のように分けています。

| 残すもの | 既定 | 選び方 |
| --- | --- | --- |
| 実行の状態・ログ・表示（図や表） | いつも残す | — |
| 部分実行に使う、各ポートの最後の入力 | いつも残す | — |
| 各呼び出しの入出力値 | 残さない | Card の `recordIO` |
| 成果物（Card が書いたファイルやフォルダ） | 残さない | Card の `retainArtifact` |
| 実行履歴をプロジェクトへ書き出す（`.tsugumi/runs.sqlite`） | 書き出す | プロジェクトの `saveRunHistory` |

`recordIO` が off のままでも、部分実行に使う最後の入力は残ります（[Q5](#q5-解析の途中からやり直せることにはどんな意味がありますか)）。長く使い続ける計算結果は Nix の出力に、試行中に見たいデータは履歴や成果物に、と目的に合わせて置き場所を選びます。

**確かめる場所**

- `recordIO` と `retainArtifact` のすべての組み合わせと、キャッシュの削除・再起動のあとに何が残るか: [test_history.py](../tests/python/test_history.py)
- キャッシュの削除や再起動のあとも、単体の実行に保存済みの入力（File の実体を含む）が使えること: [test_regressions.py](../tests/python/test_regressions.py)
- `.tsugumi/runs.sqlite` への書き出しと、コピーしたプロジェクトでの読み込み: [test_run_history.py](../tests/python/test_run_history.py)

## Q5. 解析の途中からやり直せることには、どんな意味がありますか？

**1 枚ずつ直して確かめる往復を、速くするためです。**

解析を組み立てている間は、「この Card の処理だけ直したい」「グラフの条件だけ変えたい」という場面が何度もあります。そのたびに上流から全部を動かすと、往復が遅くなります。

Tsugumi では、保存された最新入力を使って、選んだ Card だけ、またはそこから下流までを実行できます。

- 右クリックの「この Card だけ実行（最後の入力）」「ここから下流を実行」で使います。子 Workflow も同じように試せます。
- 分岐の 1 つから下流へ進めると、合流する Card は、今回届かないポートを保存された入力で埋めて動きます。ほかの分岐を動かし直さずに比べ直せます。
- 必要な入力がまだ保存されていないときは、はっきり失敗します。まず上流を含めて実行します。

使うときの注意が 2 つあります。

- **上流を変えてまだ実行していなければ、保存された入力は古いままです。** 合流で使われる値も同じです。どの実行の値を使ったかは、実行のジャーナルに残ります。
- **最後は Workflow 全体を通して確かめます。** 部分実行は、作っている途中の一部を試すためのものです。過去の入力を取り出しても、その時点のコードや上流の条件まで戻るわけではありません。

**確かめる場所**

- 画面: デモ「Cas A · Chandra RGB」で `bands` の帯域の境界（`green_min_ev` など）を書き換え、「この Card だけ実行（最後の入力）」を選ぶと、観測を読み直さずに色分けだけを試せます。
- 画面: デモ「Collatz」で `compare` を右クリックして「この Card だけ実行（最後の入力）」を選ぶと、4 言語の Card を動かし直さずに比べ直せます（先に一度全体を実行しておきます）。
- 分岐の 1 つから進めた実行が合流で保存入力と出会うこと、保存入力がないときに明示的に失敗すること: [test_scheduler.py](../tests/python/test_scheduler.py)
- MNIST のデモで、1 つの分類器だけを実行し、そこから `compare` へ進めて比べ直すこと: [test_demo_mnist.py](../tests/python/test_demo_mnist.py)

## Q6. Git と実行履歴は、それぞれ何を記録するのですか？

**Git は解析の定義を、実行履歴は動かしたときの記録を持ちます。**

| 記録先 | 残すもの | 使い道 |
| --- | --- | --- |
| Git（プロジェクトのフォルダ） | Workflow の定義、コード、params、環境の定義 | 変更をたどり、過去の版から別の試行を始める |
| 実行履歴（SQLite） | 実行の状態、ログ、表示、設定に応じた入出力値 | 実際に何が動き、どんな結果になったかを見る |

- 実行を始めると、前の版から変わっていれば保存済みの内容を commit し、その commit を実行に記録します。同じ版で何度も実行できるので、commit と実行は 1 対多です。
- 実行が終わると、その commit の note に結果を 1 行足します（`git log --notes=tsugumi` で見られます）。
- 「版として残す」で、今の内容に名前（tag）とメモを付けられます。
- 版のツリーで「この版から始める」を選ぶと、今の内容を版として残してから、その版の内容に戻ります。前の流れは消えません。

戻るのはコードと定義です。当時の worker の状態や、全データまでは戻りません。

**確かめる場所**

- 画面: デモ「Cas A · Chandra RGB」のコピーで「版の履歴」を開くと、帯域や格子を試して失敗した枝、採用しなかった枝、採用した版 `rgb-v1` がツリーで見られます。
- commit・note・tag・枝の作られ方: [test_versions.py](../tests/python/test_versions.py)、[版の管理](Versions.md)

## Q7. 未公開のデータを、AI に渡さずに扱えますか？

**扱えます。Card の計算は Mac の中の VM で完結し、外へ出るものは決まっています。**

- Card は、Mac の中の隔離された Linux VM で動きます。Card からの外部ネットワークは既定で遮断されています。
- Agent を使わず、`network: true` の Card もなければ、プロジェクトの内容やデータは Mac と VM の外へ出ません（Nix がパッケージを取得する通信を除きます）。
- Agent を使うと、会話と、Agent が読んだソース・ログ・入出力値がモデルのプロバイダへ送られます。送る内容を自動で伏せる仕組みは、まだありません。
- Agent が Card にネットワークや Mac のフォルダを与えようとする保存は、利用者の承認なしには通りません。
- 完成した Workflow の実行に LLM は要りません。公開データや合成データで Agent と処理を作り、未公開のデータでは Agent を使わずに動かす、という使い分けができます。

**確かめる場所**

- 何が守られていて、何が守られていないかの一覧: [セキュリティと隔離の要点](security.md#要点)
- Agent を使うとモデルに送られるもの: [モデルに送られるもの](security.md#モデルに送られるもの)
- Card のネットワークが既定で閉じていること: [test_workers.py](../tests/python/test_workers.py)（`test_network_is_off_unless_the_card_allows_it`）、[test_cards_container.py](../tests/python/test_cards_container.py)
- Agent が権限を広げる保存には承認が要ること: [test_permissions.py](../tests/python/test_permissions.py)
- 作るときと本番で、AI に見せる情報を分ける構想: [業務自動化とデータの境界](Vision.md#業務自動化とデータの境界)

## 補足 Q. Nix の上流参照は、どのように検証するのですか？

**保存の時点で軽く確かめ、最後は Nix の評価で決まります。**

- Card の `default.nix` からは、必ず先に実行される上流の Card の定義を `inputs.upstream.<id>` で参照できます。`inputs.local.<id>` は、そのうち同じ階層の Card だけです。
- 保存や検査のときに、ソースに直接書かれた参照をスキャナで確かめます。自分自身、存在しない Card、先に実行されるとは限らない Card（分岐の片側にしかない Card など）への参照は、`nix_reference_*` の診断としてすぐに出ます。コメントと文字列の本文は対象外で、文字列に埋め込んだ式は対象です。
- 別名や、動的に組み立てた属性名は事前には確かめません。評価器には参照してよい Card の定義しか渡さないので、それ以外を参照すると Nix の評価エラーになります。

**確かめる場所**

- 必ず先行する Card の解析（直線・分岐と `any`・`all` と optional・同じポートへの複数経路・ループ・入れ子・到達できない循環）: [tests/cpp](../tests/cpp)、[core/src/graph.cc](../core/src/graph.cc)（`compute_guarantees`）
- 仕組みの説明: [主要機能の上流定義の参照](features.md#上流定義の参照inputsupstream)
