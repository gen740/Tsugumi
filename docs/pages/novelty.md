# なぜ今、設計・実装・検証を同じ Workflow にするのか

**人間が描く仕様、AI が編集する対象、実際に動く処理を、同じ構造にする。**
Tsugumi の独自性は、この関係を Draft・Card・型・実行環境・版管理まで一貫させたことにあります。

AI が進めた解析を人間が理解し、次の条件を試すには、意図とコードと結果を結びつける必要があります。
Tsugumi では、その結びつきを Workflow として扱います。処理を示す図がそのまま実装の対象になり、実行後は結果を確かめて手を入れる場所にもなります。

## 描いた仕様が、実装と検証の場所になる

たとえば、観測データを読み、背景ノイズを推定し、モデルに当てはめ、結果を描画する解析を考えます。
最初は各処理を Draft として置き、線でつなぎます。どの処理に何を渡すかを、コードを書く前に共有できます。

Agent は説明と接続を読み、Card のコード、出力型、実行環境を作ります。出力型から下流の入力型が導出され、つながる処理の間で契約が揃います。
実行後に背景の推定方法が気になれば、その Card を開いて変更し、保存された入力で試せます。調整ができたら、全体を通して結果を確かめます。

**「ここを変えたい」の「ここ」が、仕様・コード・実行を通じて同じ場所を指す。**
そのため、解析を理解してから変更箇所を探し直すまでの距離を短くできます。

大きな処理は子 Workflow にまとめ、普段は一つの Card として扱えます。必要なときは内部へ降り、より細かい単位で確かめられます。
処理が増えても、人間が考えたい粒度で見渡せるようにする設計です。

## AI が、検証しやすい構造を作る手間を引き受ける

環境の固定、入出力の型定義、処理の分割には、検証しやすさを支える役割があります。
同時に、それらを人間が毎回手で整えるなら、短い試行にも準備の負担がかかります。

Tsugumi の Agent は、Draft に書かれた目的と前後の接続から、その準備を含めて実装できます。
`default.nix` に環境を定義し、`_outputs.fbs` に出力型を書き、C++ / Python / bash の処理を作って、実際に動かしながら修正します。
人間がすべての定義を書き始めなくても、型と環境を備えた部品を組み立てていけます。

**AI に実装を任せられるからこそ、人間が確かめやすい構造を、解析の初めから用意できる。**
これが、今 Tsugumi をこの形で作る理由です。人間は処理の目的と関係を示し、生成された実装と結果を吟味して、次の問いを立てます。

Agent と UI は、core の同じ操作と検証の規則を使います。AI が保存した Card は通常のプロジェクトファイルとして残り、人間も開いて編集できます。できあがった Workflow の実行に LLM は必要ありません。

## 型と環境が、試行の単位を支える

Card を独立して確かめるには、何を受け取り、どの環境で動き、何を返すのかを明らかにする必要があります。

| 仕組み | 明らかにするもの | 試行の中でできること |
| --- | --- | --- |
| 型付きポート | 前後の処理が受け渡すデータの構造 | 接続の型を実行前に検査し、下流の入力型を導出する |
| Card ごとの Nix 定義 | コードのビルドと実行に使う依存関係 | 環境の定義を版とともに保持し、ビルド済みの Nix の出力を再利用する |
| Card と子 Workflow | 変更して確かめる処理の範囲 | 全体を見渡し、必要な処理の内部へ降りる |
| 保存入力と実行履歴 | 次の試行に使う入力と、実行時の記録 | 一部を修正して試し直し、ログや結果を確認する |

たとえば、重いシミュレーションを seed や条件を明示した Nix のビルドとして定義しておけば、その出力を下流の解析に渡せます。下流だけを変更し、シミュレーションの定義と依存関係が変わらず、出力が Nix store に残っていれば、重い計算を繰り返す必要はありません。

runtime ではストリームや状態を持つ処理も扱えます。Nix で環境や計算を固定することと、到着順や保持状態を含むすべての実行結果を決定的にすることは区別しています。どの条件を固定するかは、解析の性質に応じて設計します。

構成の詳細は[主要機能](features.md)、再現性の考え方は [Q&A](qa.md) を参照してください。

## 試行錯誤を支える実装上の工夫

処理を小さな Card に分けるのは、人間が途中の判断を理解し、手を入れられるようにするためです。その粒度で繰り返し実行できるよう、準備・起動・保存の負担と、部分実行時の入力の扱いまで設計しています。

### 条件を変えるたびに、同じコードをビルドし直さない

解析では、コードを変えるよりも、閾値や表示条件を変えて繰り返し試すことがあります。これらをすべてビルド入力に含めると、処理の細分化が再ビルドの待ち時間を増やします。

Tsugumi は、実行時の `params.json` と Nix に渡す `params-nix.json` を分け、実行時だけのパラメータをビルド入力から外します。Card の説明や設定を含む `_meta.json`・`_card.json` も丸ごとは渡さず、ビルドに必要なソース・型・Nix 用パラメータを渡します。ビルド結果の再利用は Nix の derivation と store に任せます。

画面の配置も計算定義とは分けています。実行中に計算定義を変える保存は拒否しながら、Card の配置変更は受け付けます。**条件を試すこと、コードを変えること、画面を整理することが、それぞれ必要な処理だけを起こします。**

実装: [Nix のビルド入力](https://github.com/gen740/Tsugumi/blob/main/core/src/nix.cc)（`NixRunner::build`）、[保存の検証](https://github.com/gen740/Tsugumi/blob/main/core/src/service.cc)、[計算定義と配置の管理](https://github.com/gen740/Tsugumi/blob/main/core/src/store.cc)。検証: [共通 store の再利用テスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_shared_vm.py)（開き直し・store の掃除・プロジェクトのコピー）、[保存の契約テスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_contract.py)。

### 小さな処理を繰り返すために、評価器と worker を再利用する

数行の計算を Card に分けても、そのたびに Nix の評価器や言語処理系を起動していては、計算より準備に時間がかかります。

Nix 評価器を `tsugumid` に組み込み、nixpkgs の評価状態と daemon 接続を Card・実行をまたいで再利用します。C++ / Python の Card は、常駐 worker が共有ライブラリを読み込んで呼び出します。毎回新しい worker を使う設定でも、次の worker の起動とライブラリの読み込みを先に済ませます。

再利用する worker の状態は実行をまたいで残り、必要な初期化は `onRunStart` / `on_run_start` に書けます。失敗・取消・期限切れやメモリ上限などでは worker を終了させます。**起動の負担を減らしながら、状態を持つ計算と初期化のタイミングを明示できます。**

履歴用ディスクの分離なども含めた高速化では、C++ と Python だけだった時点の Collatz の 1,344 回の呼び出しを含む Run が、共通 VM 上の再実行で 4.5〜5.0 秒から 0.92〜1.0 秒になりました。同じ構成の初回は 7.9 秒で、初回準備と再実行を分けて計測しています（[条件と内訳](development.md#計測2026-11-03高速化後共通-vm)）。

実装: [組み込み評価器](https://github.com/gen740/Tsugumi/blob/main/core/src/nix_eval.cc)、[worker プール](https://github.com/gen740/Tsugumi/blob/main/core/src/worker_pool.cc)、[Card の呼び出し](https://github.com/gen740/Tsugumi/blob/main/sdk/src/worker_main.cc)。検証: [常駐・初期化・毎回新規の worker と取消・期限のテスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_workers.py)。

### 部分実行で、入力を集め直す手間を減らす

途中の処理だけを直して試すには、直前に何を入力したかが必要です。パスだけを保存しても元の一時ファイルが消えれば使えず、複数の入力を別々の呼び出しから混ぜれば、前回と違う条件になってしまいます。

Tsugumi は、最新の呼び出しの入力一式と、各ポートの最新入力を保存します。`all` では一回の呼び出しで使った組を保ち、`any` では各ポートの最新値を使います。File / Directory は実体を保存領域へコピーするため、実行キャッシュを消しても再利用できます。再実行時には現在の入力型との整合性とファイルの存在を確認し、不足があれば理由を返します。子 Workflow の単体実行にも、この入力を境界から渡します。分岐の 1 つから下流へ進めるときは、合流する Card のうち今回の実行で届かないポートだけをこの入力で埋めるので、変えた分岐の新しい値と他の分岐の値で比べ直せます。どの実行の値を使ったかは実行のジャーナルに残します。

**研究者は、入力を手作業で集め直さず、気になった箇所の変更を試せます。** この最新入力は、`recordIO` で選ぶ全呼び出しの入出力履歴とは別に保存します。保存時点と使い方は [Q&A](qa.md) にまとめています。

実装: [部分実行と入力保存](https://github.com/gen740/Tsugumi/blob/main/core/src/scheduler.cc)（`seed_saved`・`take_ready`・`save_last_inputs`）。検証: [キャッシュ削除・再起動後の File 入力と入力不足の回帰テスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_regressions.py)、[子 Workflow と分岐からの部分実行テスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_scheduler.py)。

### 「完了した」という表示に、保存済みの記録が伴うようにする

処理が値を返した直後に下流を進めると、その後の記録保存が失敗したとき、画面では成功していても根拠をたどれない実行が生まれます。

Tsugumi は、出力を検証し、設定に応じた成果物を保持し、呼び出しの完了記録を保存してから、完了通知と下流への値の受け渡しを行います。保存が失敗した値は下流へ渡しません。記録する入出力値には、その時点の型スキーマも保持します。画面の段階表示も、終了状態から推測せず、core が実際に記録した評価・ビルド・実行・検証・保存の段階から作ります。

**どこまで進み、どこで失敗したかを、画面と実行履歴で同じ根拠から確認できます。** 入出力値の全履歴と成果物の保持は設定で選べるため、記録量も解析に合わせて調整できます。

実装: [出力検証・保存・通知の順序](https://github.com/gen740/Tsugumi/blob/main/core/src/scheduler.cc)、[履歴と型スキーマの保存](https://github.com/gen740/Tsugumi/blob/main/core/src/history.cc)、[段階の表示](https://github.com/gen740/Tsugumi/blob/main/macOS/Sources/App/Workbench/StageLogView.swift)。検証: [履歴保存失敗の回帰テスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_regressions.py)（`test_history_write_failure_fails_the_run`）、[記録と成果物の組み合わせのテスト](https://github.com/gen740/Tsugumi/blob/main/tests/python/test_history.py)。

### 分岐を含む Workflow と、Nix の依存関係を整合させる

Card から上流の Nix 定義を参照するとき、線を逆にたどって到達できるだけでは、その Card が先に実行されるとは限りません。

例えば、A から B または C へ分岐し、どちらかの結果で D が動く場合、D に必ず先行するコード Card は A です。B と C の片方は実行されないため、D から両方の定義を無条件に参照できると、画面に描いた実行経路と依存関係が食い違います。

Tsugumi は、入力の待ち合わせ方、分岐・合流、ループ、子 Workflow を解析し、どの経路でも必ず先行する Card を求めます。`all` は必須入力が保証する集合の和、`any` や同じポートへの複数経路は共通部分を使い、ループは最大不動点で求めます。この条件を満たすコード Card の定義だけを Nix 評価器へ渡し、参照されたものを遅延評価します。

ソースに直接書かれた参照には、保存・検査時に早期診断も行います。別名や動的な属性名など、早期診断の対象にならない書き方でも、評価器に渡す参照範囲は同じです。

**Workflow の接続関係を、実行順だけでなく、環境定義の依存関係にも反映できます。**

実装: [必ず先行する Card の解析](https://github.com/gen740/Tsugumi/blob/main/core/src/graph.cc)（`compute_guarantees`）、[Nix へ渡す上流定義](https://github.com/gen740/Tsugumi/blob/main/core/src/nix.cc)（`entry_nix`）。検証: [分岐・合流・ループ・子 Workflow のテスト](https://github.com/gen740/Tsugumi/blob/main/tests/cpp/core_tests.cc)（`upstream_branch_sides_do_not_survive_any_merge` など）、[早期診断の範囲（Q&A の補足）](qa.md)。

## 一つの結果から、別の仮説へ進める

研究では、うまくいった結果の先にも問いが続きます。
条件を変える。別のモデルを試す。以前は採用しなかった方針へ戻る。そのたびに、どの版の処理で何を試したかをたどれることが重要です。

Tsugumi は、コードや Workflow の定義を Git で管理し、実行にその版を関連づけます。
版のツリーから以前の内容へ戻って別の試行を始められ、ログや表示結果は実行履歴から確認できます。
入出力値の履歴を残すかは `recordIO`、成果物を保持するかは `retainArtifact` で選びます。部分再実行用の最新入力は、全呼び出しの入出力履歴とは別に保存します。

**コードを残すこと、結果を読むこと、次の条件を試すことが、一つの研究の流れになる。**
部分実行で処理を調整し、最後は Workflow 全体を通して確かめる。この往復を支えるために、版管理と実行履歴を組み合わせています。

操作と保存の仕組みは[版の管理](versions.md)、記録と再実行の設計意図は [Q&A](qa.md) にまとめています。

## 既存のアプローチに重ねて、何を一体化するのか

対話しながらコードを試すこと、処理をグラフで表すこと、依存関係や版を管理することは、それぞれ既存のアプローチにある考え方です。
Tsugumi では、それらを次のようにつなぎます。

| アプローチ | Tsugumi でのつなぎ方 |
| --- | --- |
| コードを動かし、結果を見ながら考える | Card の結果からその処理を開き、保存入力で変更を試す |
| 自然言語で AI に実装を依頼する | Draft の説明に接続関係を加え、実装後も同じ Workflow を共有する |
| グラフで処理の関係を表す | 表示された接続を型の導出と実行の規則に反映する |
| 環境・コード・実験の版を管理する | 実行をコードの版に関連づけ、過去の版から次の試行を始める |

これを支える個々の仕組みは、それぞれの文書で説明しています。Card の隔離は[セキュリティと隔離](security.md)、C++ Card を共有ライブラリとして呼び出す worker は[Card SDK と worker](features.md#4-card-sdk-と-worker)とその[計測](development.md#計測2026-11-03高速化後共通-vm)、分岐・合流・ループの規則は[実行の意味論](features.md#実行の意味論スケジューラー)、テキストファイルとしての保存は[文書と保存](features.md#5-文書と保存)を参照してください。

**Tsugumi が目指すのは、人と AI が同じ構造を使って設計し、動かし、考え続けられる研究環境です。**
その構造があることで、研究者は AI の進めた試行に立ち戻り、自分の疑問を具体的な変更として試せます。
研究を出発点に、この関係を学習・開発・引き継ぎへ広げる構想は [Vision.md](vision.md)、制作の背景は [Philosophy.md](philosophy.md) を参照してください。
