## A. Project layout (representative Code Card)
```
<project>/
├── tsugumi.json        # name, canvas (cards, connections), nixPath (intent)
├── tsugumi.lock        # { entries: [{ name, url, rev, narHash }] }
├── layout.bin          # FlatBuffers binary: UI presentation (positions, flow, note geometry/color/scope)
├── notes/<id>.md       # sticky-note text, plain Markdown
├── externals/<id>/     # an imported (copied) project; self-contained (own tsugumi.json + lock)
├── .tsugumi/           # run data (history db, artifacts, ...); project-local, never versioned
└── definitions/<id>/   # the id is the ONLY name of a Card (no title)
    ├── _card.json      # type, input port names; other existing fields (external, sandbox, timeouts, ...) stay; NO param declarations or values
    ├── _outputs.fbs    # output port types; outputs without (required) may be omitted
    ├── _inputs.fbs     # GENERATED by core (see C)
    ├── params.nix      # the Card's params: a flat literal-only attrset holding the current values
    ├── default.nix     # { params, inputs }: -> { run; api?; views?; exports?; }
    ├── README.md       # front matter `description: <one line>` only; body = the description text
    ├── _comments.json  # review comments (JSON text, .fbs schema)
    ├── src/
    └── views/          # optional own view sources
```
- The tree shows a Code Card. An Input Card has the same definition files (params.nix + default.nix, see C); Draft, Trigger and subgraph keep their own shapes.
- Text project documents (tsugumi.json, tsugumi.lock, _card.json, _comments.json) are JSON text whose schema is in .fbs, read/written with the FlatBuffers parser; so every document shape must be expressible as an .fbs table (hence the lock is a list, not a map). Machine-only JSON inside core becomes FlatBuffers binary. JSON stays where Nix reads it. **[impl]** JSON at the Agent/LLM boundary stays.
- `_meta.json` is gone: its prose → README.md, its comments → `_comments.json`, its `outputs` field is deleted.

## B. nixPath and the lock
- `tsugumi.json` `nixPath: [{ name, url }]` — intent, written by a person or the Agent. Different versions of one package are different names (`nixpkgs`, `nixpkgs-2505`).
- `tsugumi.lock`: a root table `{ entries: [{ name, url, rev, narHash }] }` (a list; the root object is only because .fbs needs a root table) — `url` is the declared url (so a changed declaration is detectable), `rev` locates the source, `narHash` verifies it. No transitive entries.
- Update (explicit only, one name or all; core uses Nix's fetcher): a declared name missing from the lock is added; a lock entry whose name is no longer declared is deleted; an entry whose declared url changed is treated as new and re-resolved; everything else is kept as is.
- Evaluation uses only the lock; a declared name without a lock entry, or whose url differs from the lock's, is an error asking for an update.
- Each project (root or externals/<id>) resolves only against its own nixPath and lock; no inheritance either way.
- Copying a Card into another project does NOT carry declarations; an undeclared `<name>` errors and a person or the Agent adds the line.
- Flake-only repositories are not supported.

## C. Card definition, build and evaluation
- `default.nix` is `{ params, inputs }`. No `pkgs`, no `schemas`. A Card writes `pkgs = import <nixpkgs> { }` and e.g. `sdk = import <tsugumi-kit/sdk/cpp> { inherit pkgs; }`.
- `params` = the evaluated params.nix. params are BUILD-TIME ONLY: the SDK embeds them into what it builds; there is no `CardInput.params`, no second channel. A derivation depends only on the values that flow into it (plain Nix). No `nix: true` flag, no run/build split. Builders take params as an evaluated value (`params` argument / `import ./params.nix`), never as a path (interpolating the path copies the file and rebuilds on every change).
- `params.nix`: flat literal-only attrset (`{ seed = 7; tariff = "spot"; }`). Value types: bool, int (= int64), float (= double), string, and lists of these; every param has a value; no empty lists; no uint64; `10` and `10.0` differ. The UI changes a value by rewriting that literal in place (keeping its type, the rest of the file and comments). Core evaluates it with builtins only, checks it is literal-only, caches by content hash.
- Variants: there is NO sweep feature. Variants always come from the Card's `default.nix` returning a `run` LIST (`[{ label; run; }]`), built and parallelised by Nix; params.nix may hold a plain list (e.g. `sweep = [ 1 2 3 4 ];`) that default.nix maps over. Combinations across Cards are core batch axes (Cartesian product); data just flows. A downstream Card rebuilds only when something its default.nix uses changed; port data never triggers a rebuild.
- **Input Cards** also have a `default.nix` and a `params.nix` (owner). The values live in params.nix; a kit helper (e.g. `sdk.input { values = params; outputs = ./_outputs.fbs; }`) builds the output bytes with flatc as a small derivation; the core only emits those built bytes. Value variants are a `run` list. **[impl, proposal]** a file input is a file placed in the Input Card's build output, which the core exposes downstream as a read-only Artifact (the store path is already immutable, so no copy). This also simplifies pack.
- `inputs` = Nix values only: the exports of every upstream Card guaranteed to run first, as `inputs.<card_id>.<attr>`, chosen by graph connectivity (not by port, separate from data wires). Example: `A → B → C` gives C both `inputs.A` and `inputs.B`. **[impl, my proposal, not confirmed]** through a Merge, only upstreams common to all of its inputs; nested Cards keyed by full path.
- `_inputs.fbs` is generated by core from the wiring and the upstream `_outputs.fbs`, written into `definitions/<id>/` with a header marking it generated, refreshed when the wiring or an upstream `_outputs.fbs` changes and at the latest before that Card is evaluated, and versioned like any project file. Unconnected ports are not listed. A Merge-fed port is the candidate type itself when all candidates are the same type, otherwise a union of the candidate types. Each candidate type carries, as an attribute written by the core, the schema id the core stamps on values of that type (D), so the SDK matches incoming values to candidates by reading the file; core and SDK never compute ids independently. Builders read `./_inputs.fbs` and `./_outputs.fbs` directly.
- Card result: `run` (lib/main.so, or a run list), `api` (owner-required mechanism: a light codegen-only derivation whose output holds the readable API under `share/tsugumi/api/`; a Card without `api` simply has nothing to show), `views`, `exports`.
- Evaluator: core fetches locked sources (if not in the store) and verifies narHash, maps `name=<store path>` on the search path and allows those paths plus the Card's own directory; never reads the host NIX_PATH; undeclared `<name>` errors; IFD forbidden; a Card expression never fetches. `builtins.currentSystem` is set to the system that runs the Card (so `import <nixpkgs> {}` is right with nothing special-cased); evaluator state and cache are keyed per system.
- Generic evaluation tool (replaces CardApi): evaluates a short Nix expression in the Card's directory (relative paths, nixPath names, `params`, `inputs` in scope), for the local system only; evaluation only unless an explicit build realises a derivation and returns its files (bounded). No `card` binding, no system switch; the idiom `(import ./. { inherit params inputs; }).api` is documented in the Agent skill. "Build SDK" in the Mac and Web UIs builds `.api` through it and shows `share/tsugumi/api/` read-only (and build failures there).
- Removed here: `inputs.tsugumi` (bundled kit), `pkgsPath`, `nixSources` (+ its evaluator and resolve RPC).

## D. Card ABI (version 0 until v1.0.0; at v1.0.0 it becomes 1; names carry no number)
- Entry `tsugumi_main(call, result)`; fixed CardInput / CardResult / CardFailure. CardInput carries the arrived connected inputs only (no params).
- `CardPort { name; schema; bytes; artifacts:[ArtifactId] }`. `schema` identifies the value's type so the SDK can interpret the bytes using the fbs information; the core computes it (one rule, in core only) from the producer's declared output type, stamps it on values and writes it into `_inputs.fbs` (C); it never opens the bytes. **[impl]** the rule = sha256 of a canonical bfbs of that type. No `path` field, no Path/FlatBuffer kind.
- Effects: `send(view, bytes, size)`, `recv(view, out, timeout_ms)`, `cancelled`, `remaining_ms`, `artifact_create`, `artifact_open`.
- `TSUGUMI_MESSAGE_MAX` = 2^24 bytes (16 MiB) per message; a larger send errors immediately; SDKs split big data and views reassemble.
- Backpressure hop by hop (Card→worker, worker→tsugumid, tsugumid→UI, UI→view): every hop holds at least one max-size message (≥2 advised; depth not in the contract) and forwards only when the next hop has room for one. Card `send` blocks (cancellable) while the worker has no room for one message. Card `recv` blocks until a message, the timeout or cancellation (0 message, 1 timeout, 2 cancelled, <0 error). View `tsugumi_view_send` never blocks and returns negative when there is no room (also when no Card is listening). `send` and `recv` (only these two effects) are valid for the whole process lifetime, also from a Card's own threads after the call returns; `recv`'s returned bytes stay valid until the next `recv` on that thread **[impl]**; `cancelled` in `recv` outside a call means the process is being stopped **[impl]**. No receiver (no UI has the view open) → tsugumid discards.

## E. Artifacts (replace Path, CardPort.path, output path collection, retainArtifact)
- Type: `struct ArtifactId { bytes:[ubyte:16]; }`, `table Artifact { id:ArtifactId (required); }`. id = unguessable random 128-bit capability; no path in data. Directories only (a file = a one-file directory; SDK convenience).
- ABI: `typedef struct { uint8_t bytes[16]; } tsugumi_artifact_id;` `artifact_create(host, tsugumi_artifact_id* id, tsugumi_bytes* path)` → a new writable directory for this call, sealed read-only when the call returns; `artifact_open(host, const tsugumi_artifact_id* id, tsugumi_bytes* path)` → read-only path, only for ids granted to this call; opened lazily.
- An `Artifact` may be embedded anywhere in user data (inside tables, vectors, unions).
- Grants: the SDK fills `CardPort.artifacts` from its own data, including every nested `Artifact`; core grants a call exactly the ids in its input CardPorts; an output may list ids created in this call or granted to it (forwarding = listing a granted input id; no copy), anything else is rejected. Merge forwards the whole envelope including `artifacts`; Collect keeps each element's ids and they are granted downstream. The sandbox shows only opened artifacts.
- Storage under `.tsugumi/artifacts/<run-id>/...` (run-id separation is the owner's, so people delete per run), managed by core like the history db. **[impl]** further levels (card, invocation) and the db columns. Remote artifacts are copied back with the result. No auto-deletion.
- SDK API: dir(), upload() (= create + copy), open(); codegen-bound to Artifact. A kit test checks that every Artifact in the SDK's data is listed in `CardPort.artifacts` (an omission only makes it unopenable).
- Access mechanism (owner, revised 2026-11-24): the artifact store is never visible to a Card. Each invocation gets its own directory under .tsugumi/ (same filesystem as the store). Granted input artifacts are placed there as links: hard links on Linux (the input directory mounted read-only, so writes and chmod fail with EROFS), clonefile copies on macOS. A directory artifact is recreated with each file linked. Outputs are written into the invocation directory and moved (rename) into the store by the worker afterwards, then sealed. `artifact_open` at run time checks the grant in core's records, links the artifact into the invocation directory and returns its path. Listing the invocation directory shows only what the Card may use. No execute-only (0311) holders. With isolation off nothing is guaranteed. (Replaces the 0311 design, which Apple's virtiofs cannot traverse.)

## F. Graph semantics and built-ins
- One wire per input; a second wire into an input is a wiring diagnostic naming Merge (no type comparison). One output may feed several inputs (already allowed in the graph code); the same bytes are passed by reference.
- A normal Card runs only when ALL its connected inputs have arrived; there is no per-Card "any input" setting.
- Skip rule: a normal Card is skipped when any of its connected inputs can never arrive (its producer finished without that output, or was skipped). Merge forwards whatever arrives and is skipped only when none of its inputs can arrive anymore without any having arrived. A skip is recorded, shown distinctly from success and failure, and propagates. **[impl]** Collect with no members emits an empty `Collected`.
- Outputs with `(required)` must be produced (else the SDK raises output_invalid); others may be omitted — that is how a Card branches.
- Built-ins for routing/aggregation are only Merge and Collect (Input, Draft, Trigger, subgraph remain as Card kinds). Merge runs on any one arrival and forwards the envelope unchanged (skip as above); its output type for codegen is the candidate types (a union in `_inputs.fbs` when they differ, the type itself when all are the same). Collect turns a batch into one core-fixed `Collected` list of opaque envelopes (schema, bytes, artifact ids); skipped members are absent.
- The core never opens, verifies, branches on or rebuilds a user port payload. It still checks fixed envelopes, sizes, grants and filesystem boundaries, evaluates params.nix and generates `_inputs.fbs`.
- The UI shows a Merge output's type as `A | B` from the candidate names the core reports; that string is presentation only and never reaches builders.

## G. Display
- Views: top-level `views = [ { name; type = "html" | "dawn"; blob; } ]` in default.nix, supplied by the SDK or the Card, fixed at build time and shown before a run starts; several views per Card. `html` = one self-contained HTML file (JS and embedded Wasm allowed); `dawn` = a Wasm binary drawing on one WebGPU canvas. Core serves declared blobs opaquely and relays messages Card ↔ worker ↔ tsugumid ↔ UI ↔ view (never a direct socket); the UI resolves names and shows errors for undeclared or duplicate names. Nothing in the display path is recorded for now. For now LineChart/Points etc. are SDK html views.
- Views receive data messages only (no core `{type:"run"}` messages, no core "latest only" rule); pacing is the Card's responsibility through the blocking send.
- html views: a MessagePort, bidirectional.
- dawn view ABI 0: see `view-abi-draft.md` — imports only a webgpu.h subset plus `tsugumi_view_send` and `tsugumi_view_read`; required exports memory/abi/start/resize/draw; optional message(size)/pointer(scalars)/key(scalars); the host never allocates in or writes the module's memory on its own (the view gives `read` a destination it allocated); the host calls `draw` right after `start`; one instance per view; all calls on one thread. **[impl]** exact webgpu import list and headers revision, fixed with the host.
- One UI per project: a second UI connection is refused (the first keeps the project). This concerns UI connections, not the Agent/CLI.

## H. Roles
- The Card ABI exposes effects. The SDK connects language-level types (typed ports from `_inputs.fbs`/`_outputs.fbs`, Artifact, views, params embedding) to them and interprets fbs + bytes. The core manages storage (history db, artifacts), grants, sealing, `_inputs.fbs` generation and the relay.

- pack debug builds (owner, 2026-11-25): an export option builds a debug app that keeps a local client endpoint (a unix socket readable only by the user). Through it a test script (or the Agent) uses the same API the Agent uses:
  - list windows (sessions);
  - send view input (pointer, key, text, gamepad) and take snapshots;
  - inject typed port values (fbs) into any Card's input and start from that Card;
  - read run records and outputs;

  Release exports drop all of it: no endpoint, fixed values (the "no recipient overrides" decision still holds for release apps).
- View input and snapshots for the Agent are one hostd API that the Agent tools and the client libraries both use.
- Card result ownership (owner, 2026-11-25): once tsugumi_main returns, the result buffer belongs to the host. SDKs allocate it with libc malloc and keep no global result buffer; the host frees it with free after its last reader (in pack the readers are known at export). No release function.
- pack execution (owner, 2026-11-25):
  - Default: one resident process per Card plus shared memory for result buffers (zero copy), keeping Tsugumi's semantics, reuseWorker included.
  - Export option "fast": every Card's main.so is loaded into one process at start and Cards are connected by plain calls passing fbs buffers, with no copies and no locks. Threads appear only at fan-out, and Cards manage their own threads. This option does not follow reuseWorker (everything is resident) and has no memory or crash isolation. It is a choice of speed over Tsugumi's exact environment, not an isolation knob.
  - Language runtimes are initialised once per process by their SDK and shared. Go allows only one Go library per process, so the fast option refuses more than one Go Card.
  - Every Card's `systems` must include the target system of the export, else the export fails.
  - Release exports keep fixed values; debug exports keep the client endpoint (see "pack debug builds").
- Deleted artifacts leave nothing (owner, 2026-11-25): deleting a run's artifacts removes content and db rows; no tombstone. Remove the tombstone TODO in #446.
- Sandbox flags by meaning on macOS (owner, 2026-11-25): `pid` = cannot see or signal processes outside its own tree; `ipc` = cannot reach shared memory, semaphores, SysV IPC, Mach services or unix sockets it was not given; `identity` = cannot use the user's credentials (home files, keychain, other apps' data, user network credentials); on Linux identity is also a separate uid. macOS implements all three with Seatbelt rules and reports them as available, so Cards that ask for them run natively (tsugumi web on a Mac). Found because #440 made every Card state pid/ipc/identity: true and the macOS native runtime refused them.
- Demos (owner, 2026-11-25): keep report, collatz, signal-sweep, live-stream, glowroot, point-cloud, casa, gw150914, csharp-calibration, ruby-pipeline, go-pipeline, rust-pipeline, max-flow and gw150914-draft (en and ja); remove the rest; port the kept ones to the current ABI and views, add aarch64-darwin, re-enable demo tests; pack README example becomes glowroot.
- Native pack answers (owner, 2026-11-25):
  1. A `result_alloc(host, size)` effect: the host lends the result buffer (plain memory in-process, shared memory across processes); "after return the result belongs to the host" stays.
  2. Card input becomes an array of {name, schema, bytes span} borrowed from upstream buffers (zero copy), replacing the single CardInput flatbuffer.
  3. Fast mode stops Cards cooperatively only; a Card that misses its hard deadline stops the whole app with an error (the price of no isolation).
  4. Fast mode bundles one copy per runtime version and shares it; conflicting runtime versions refuse a fast export.
  5. In packed apps the result handoff is trusted (Cards are fixed at export and shipped by one author); documented. Dev Tsugumi keeps its sealing rules.
