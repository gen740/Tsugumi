# Releasing Tsugumi

Run commands from the repository root. Replace `<version>` with the numeric `major.minor.patch` to publish and `<number>` with its release-candidate number; choose an untagged version at least as high as the existing tags. Build instructions are in [Installing and building](docs/INSTALL.md#building-from-source).

- **The version number** is only in `VERSION` (read by the core, Nix, CMake and the app).
- **Making a release**: in a clean checkout whose HEAD is origin/main, `macOS/tools/release.sh <version>` sets `VERSION`, commits it if needed and pushes main with the tag `v<version>`. Without a checkout, `gh workflow run release.yml -f version=<version>` (Actions does the same). Either way the release workflow (`.github/workflows/release.yml`) builds the app and creates a GitHub Release, which installed releases find and update to automatically (`macOS/Sources/App/Model/Updater.swift`).
- **Making a release candidate**. Run `macOS/tools/release.sh <version>-rc.<number>` from a checkout of origin/main. `VERSION` and the packaged app and command report the numeric `<version>`. The workflow publishes the suffixed tag as a GitHub prerelease. Download the app from the candidate's release page. Set `TSUGUMI_VERSION` to `<version>-rc.<number>` when running a CLI installer for the candidate. The app's automatic updater follows stable releases. The app needs a manual reinstall to switch to the stable release of the same numeric version. The `tsugumi update` command uses the latest stable release.
- **The `tsugumi` command**: the same workflow puts `cli/install.sh`, `cli/install.ps1`, and the `tsugumi-macos-arm64.tar.gz` and `tsugumi-linux.tar.gz` made by `cli/package-macos.sh` and `cli/package-linux.sh` (each with a `.sha256`) on the release. Publish the installers and distributions together so `releases/latest/download/` serves matching versions. The Node.js version and checksums are in `cli/node-version.env`. To try it locally, pass a folder holding the distributions as `TSUGUMI_INSTALL_BASE=file://…`, and keep the VM apart with `TSUGUMI_SUPPORT_DIR`.
- **The VM's boot disk** (`macOS/Container/vm-boot.nix` and the pinned nixpkgs): after changing it, publish it to [gen740/tsugumi-vm](https://github.com/gen740/tsugumi-vm) before releasing, with `macOS/Container/build-image.sh --vm` and `macOS/tools/publish-vm.sh` (which also publishes the list of licenses and the corresponding source with the disk). The runners cannot use Apple container, so the release build fails without a published disk.
- **Development and release versions** (`macOS/Sources/Launcher/AppChannel.swift`): `build-app.sh` makes the development version by default (`Tsugumi Dev`, bundle id `app.tsugumi.Tsugumi.dev`, `TsugumiChannel` `dev` in `Info.plist`), and with `--release` the release (`Tsugumi`, `app.tsugumi.Tsugumi`, `release`). The support folder (VM, store, control folders, conversation history) is `~/Library/Application Support/Tsugumi-dev/` for the development version and `Tsugumi/` for the release, and agentd's settings and credentials are separate under those support folders too; presentation preferences use each app's UserDefaults. Checks and tests during development (UI scripts, smoke, `swift test`) use the development version, so they never touch the VM of the release you use. The Python tests' shared VM is `build/test-vm`.
- **Signing development builds**: by default both are signed ad hoc. The development version can be signed with a certificate in this Mac's keychain (Apple Development or the like) named in the environment variable `TSUGUMI_CODESIGN_IDENTITY`: `TSUGUMI_CODESIGN_IDENTITY="Apple Development" macOS/build-app.sh` (part of the certificate's name, or its SHA-1, as `codesign --sign` takes; list usable certificates with `security find-identity -v -p codesigning`). This gives the app a stable designated requirement across rebuilds. `--release` ignores the variable and stays ad hoc (release artifacts do not depend on the environment). The `com.apple.security.virtualization` entitlement the VM needs is attached with either signature. API keys saved by the Mac app live in the login Keychain. With an ad hoc signature, macOS treats each rebuilt binary as a different program and may show a Keychain permission dialog. A certificate and bundle id keep that identity stable across rebuilds.
- **Automatic updates** happen only in releases. 20 seconds after launch and every six hours, the app reads `api.github.com/repos/gen740/Tsugumi/releases/latest`, and if a version newer than the current one (not a draft or pre-release) has `Tsugumi.zip` and `Tsugumi.zip.sha256`, downloads them into a temporary folder on the same volume as the app and checks the checksum, `codesign --verify --deep --strict`, the bundle id, `TsugumiChannel` and the version number. The replacement happens in `applicationWillTerminate` (the resident execution environment remains independent) with `FileManager.replaceItemAt`; for "Restart to Update", the new app is opened after waiting for this process to end. No checks happen while a UI script or smoke run is going.
