# Tsugumi は n8n や KNIME と何が違うのか

n8n も KNIME も Tsugumi も、「箱（ノード / Card）を線でつないで処理を組み立てる」という画面上の見た目はよく似ています。
しかし、それぞれのツールが解こうとしている課題はまったく異なります。

- **n8n** は、SaaS や外部 API をつなぐ**業務自動化**のためのツールです。Webhook やスケジュールを起点に、Slack・Google Sheets・CRM など数百種類の連携ノードを介してデータを運ぶことが得意です。
- **KNIME** は、GUI ベースの**データ分析プラットフォーム**です。表データ（data table）を中心に、読み込み・前処理・統計解析・機械学習・レポート出力までの豊富なノードをノーコード／ローコードで組み合わせることが得意です。
- **Tsugumi** は、**自分で書いたコード（C++ / Python / bash）を、実行環境ごと固定し、いつ・どこで動かしても同じ結果が出る形で実行して、すべての過程を記録する**ための研究ワークベンチです。計算・シミュレーション・データ処理のパイプラインを「再現可能な実験」として扱うために設計されています。

以下では、Tsugumi の強みを 8 つの観点から具体的に説明します。あわせて最後に、n8n や KNIME を選ぶべき場面も率直に挙げます。

## 1. 環境まで含めて再現できる（Nix）

n8n の Code ノードや KNIME の Python ノードは、原則として**そのマシンに入っている** Node.js や Python、ライブラリを使って動きます。KNIME では conda 環境を指定できますが、環境の中身（ライブラリの細かなバージョンやネイティブ依存）はマシンごとに解決されます。そのため、半年後に別の Mac で開くとライブラリの更新によって結果が微妙に変わる、といったことが起こりえます。

Tsugumi では、**Card ごとに `default.nix` で実行環境を宣言**し、nixpkgs のリビジョンとハッシュまで厳密に固定します。

```nix
{ pkgs, inputs, params }: {
  run = inputs.tsugumi.cppCard { sdk = inputs.tsugumi.sdk { languages = [ "cpp" ]; }; src = ./src; };
}
```

- コンパイラ・インタプリタ・依存ライブラリのバージョンはすべて Nix のハッシュで一意に決まります。同じ定義であれば、どの Mac で動かしても同一のバイナリが使われます。
- Card ごとに環境が独立しているため、「この Card は古い NumPy、隣の Card は新しい NumPy」といった構成でも一切衝突しません。
- 評価には restricted eval と IFD（Import From Derivation）禁止を適用しており、宣言されていない外部ファイルやネットワークへ暗黙に依存する定義は書けません。
- 独自のキャッシュ機構ではなく Nix の derivation そのものでビルドの要否を判定するため、「古いキャッシュが残っていて結果が食い違う」という問題が起きません。

**「同じ入力・同じ定義なら、必ず同じ結果になる」ことをツールの仕組みとして徹底している**点が、Tsugumi の最大の特徴です。

## 2. 型のあるポート

n8n はノード間を JSON（items の配列）で受け渡し、KNIME は列の型を持つ表を受け渡します。どちらも柔軟ですが、「このポートに実際にどんな構造のデータが流れてくるか」は動かしてみるまで分からないことが少なくありません。

Tsugumi のポートは **FlatBuffers のスキーマによって静的に型付けされています**。

- 出力の型を `_outputs.fbs` で宣言すると、下流 Card の入力型は自動的に導出されます。合流（merge）では自動で union 型が生成されます。
- ポートをつないだ時点で構造的な互換性を検査するため、型の合わない配線は実行する前に検出できます。
- C++ では `input.number.value` のように、ポート名がそのまま型付きのメンバとして生成されます。JSON のキー名を文字列で引いてタイプミスに悩まされることがありません。
- 64 bit 整数・enum・struct・union・ファイル・ディレクトリを、C++ / Python / bash の間で一切の欠落なく受け渡せます（JSON を介した際に 64 bit 整数が浮動小数点に丸められて精度を失う、といった問題が起きません）。

## 3. 本格的なプログラムを高速に動かせる

n8n の Code ノードは JavaScript / Python の短いグルースクリプト向けであり、KNIME の重い処理は Java 製ノードか外部の Python / R プロセスとの連携が中心です。**C++ で書いた計算コードをそのままノードとして高速に回す**用途は、どちらも想定していません。

Tsugumi は C++ を第一級の言語として扱います。

- C++ の Card は共有ライブラリ（`lib/main.so`）としてビルドされ、worker プロセスがメモリ上に読み込んで直接関数を呼び出します。呼び出しのたびにプロセスを起動したり、標準入出力のテキストへシリアライズし直したりするオーバーヘッドがありません。
- worker は実行をまたいで常駐し、メモリ上の状態を保持できます。また、次回使う worker を裏で先行起動しておくこともできます。
- 実測では、C++ Card 1 回の実行段階は平均 0.26 ms、Collatz デモの 1,344 回の呼び出し全体が 0.92〜1.0 秒で完了します（共通 VM 上、2 回目以降。[開発資料の計測](Development.md)）。
- Python・bash も同じ型契約の上で混在でき、「C++ と Python の独立した 2 つの実装に同じ入力を流し、結果が完全一致するかを 1 つのグラフ上で検証する」といった実験が自然に組めます（`collatz` デモ）。

## 4. 厳密な意味論を持つ制御フロー

n8n には IF / Switch / Merge / Loop があり、KNIME にもループや条件分岐のノードがあります。Tsugumi の特徴は、これらの制御フローを**スケジューラーの意味論として厳密に定義している**点にあります。

- 入力の待ち合わせ方（`all`：全入力が揃ったら 1 値ずつ消費 / `any`：到着順に消費）と、有界キューによる背圧（バックプレッシャー）。
- 条件分岐（branch）で選ばれなかった経路の下流は `skipped`、未実装の Draft や上流の失敗に依存する経路は理由付きの `blocked` となり、それらと独立した経路は止まらずに最後まで進みます。
- フィードバックループは `maxRuns` で反復上限が保証され、意図しない無限ループで暴走しません。
- Card in Card（子 Workflow）は、外からは通常の Card と同じように配線・実行でき、内部だけを単体で再実行することもできます。
- さらに Nix の環境定義から「どの経路を通っても必ず先に実行される上流 Card」の定義を参照でき、その可否は分岐・合流・ループ・入れ子を考慮した静的解析によって判定されます。

## 5. すべての実行を記録し、途中からやり直せる

n8n の実行履歴（execution）は基本的に「直近でどう動いたか」を確認するためのもので、保存期間や容量の上限で消えていきます。KNIME はノードの出力を表として保存できますが、過去の試行との体系的な比較には別の仕組みが要ります。

Tsugumi は、**試行錯誤の履歴そのものを研究の記録として残す**ように設計されています。

- 呼び出しごとに、どの段階（評価・ビルド・実行・保存）に何ミリ秒かかり、キャッシュが使われたか、どの出力ポートへ値を送ったかをすべて記録します。
- 入出力の値は FlatBuffers のバイト列のまま、その時点のスキーマ（型定義）と紐づけて保存されます。後から Card の型定義を変更しても、過去の実行記録を正しく復元して読めます。
- 完了した実行履歴はプロジェクト内の `.tsugumi/runs.sqlite` にも書き出されるため、フォルダごとコピーしたり別の Mac へ移したりしても履歴がそのまま引き継がれます。
- 保持された成果物（ファイル・ディレクトリ）は改ざんを検出できます。
- 「前回保存された入力を使って、この Card だけを再実行する」「ここから下流だけを再実行する」ことができるため、途中の処理を手直ししながら検証を重ねる研究のサイクルに直結します。

## 6. Card ごとの強固なサンドボックス隔離

n8n のノードは基本的に n8n 本体と同じプロセス・同じ権限で動作し、Code ノードからサーバーの環境へアクセスできます。KNIME のノードもデスクトップアプリと同じユーザー権限で動作します。

Tsugumi の Card は、**Mac 本体から隔離された Linux VM の中で、さらに bubblewrap のサンドボックスに入れて**実行されます（詳細は [security.md](security.md)）。

- Card はデフォルトでネットワークも Linux capability も持たず、見えるファイルは読み取り専用の `/nix/store` と自身の入力・一時作業領域だけです。外部との通信や Mac 側フォルダへのアクセスは、設定（`network`・`hostFolders`、Experimental）で明示した Card にしか許されません。
- プロジェクトごとに専用の uid・名前空間・cgroup が分離されており、あるプロジェクトの Card が別プロジェクトのデータやプロセスを覗き見ることはできません。
- Mac 側から VM に共有されるのは、現在開いているプロジェクトのフォルダと、Card 定義やチャットで明示的に指定されたフォルダだけです。

そのため、外部から受け取った Card や AI が生成したコードを、Mac 本体の環境を汚したり危険にさらしたりすることなく安全に試せます。

## 7. 人が読めるテキストファイルとしての Workflow

n8n のワークフローはデータベース内に保存され（JSON エクスポートは可能）、正本はサーバーの中にあります。KNIME のワークフローはフォルダ構造ですが、中身は XML や独自形式のファイルに分かれており、Git の diff を人間が読んで変更意図を理解するのは困難です。

Tsugumi のプロジェクトは**見通しのよい通常のフォルダ**です。

- `tsugumi.json`、`definitions/<Card>/_card.json`、`default.nix`、`src/*.cc`、`src/*.py`、`_outputs.fbs`、`layout.json` など、すべて人間がそのまま読めるテキストファイルで構成されています。
- 計算の定義（Card の処理や配線）と画面上の見た目（配置座標・付箋・グループ）はファイルが分離されているため、Git の差分から「計算ロジックが変わったのか、配置を整えただけなのか」が一目で分かります。
- 保存処理はジャーナル付きのトランザクションで行われ、万一途中で異常終了しても「全件適用」か「全件未適用」のどちらかにしかなりません。UI と Agent が同時に編集した場合もリビジョンで競合を検出し、互いの変更を黙って上書きしない仕組みになっています。

## 8. AI が「検証可能な部品」を作る

n8n の AI Agent ノードや KNIME の AI アシスタントは、主に「ワークフローの実行中に LLM を呼び出す」か「GUI 操作を補助する」ためのものです。

Tsugumi の Agent は、**人間による全体の設計と、AI による個別処理の実装・検証を分担する**ために作られています。

- 人間は Canvas 上に **Draft**（概要・処理内容・仮の入出力）を置いて先に配線し、パイプライン全体の骨格を描きます。
- 「Card を生成」を実行すると、Agent が Draft と前後の配線から入出力の型・Nix 環境・ソースコードを作成し、1 つのトランザクションとして保存したうえで実際に動かして検証します。途中で失敗したりキャンセルしたりした場合は、中途半端な変更を残しません。
- Agent が使うツールはすべて core の RPC 契約（FlatBuffers スキーマ）から自動生成されており、UI とまったく同じ検証ルールのもとで動作します。
- 生成されたコードも §6 のサンドボックス内で動くため、AI が書いたコードを安心して実行できます。
- なお、Workflow の実行自体に LLM は不要です。Agent を一切使わなくても、すべての作成・編集・実行は画面から完結します。

## 9. 比較のまとめ

| 観点 | n8n | KNIME | Tsugumi |
| --- | --- | --- | --- |
| 主な用途 | SaaS / API 連携の業務自動化 | データ分析・機械学習 | 自作コードによる再現可能な計算パイプライン |
| 実行環境の固定 | マシンの Node.js / Python | マシンの Java / conda | Card ごとに Nix で固定（ハッシュ単位） |
| ノード間のデータ | JSON の items | 型付きの表 | FlatBuffers スキーマによる静的な型付き値 |
| C++ のコード | 不可（JS / Python） | 限定的 | 第一級（共有ライブラリをメモリ上で直接呼び出し） |
| 実行の隔離 | 本体と同じプロセス・権限 | 本体と同じ権限 | Linux VM + bubblewrap（デフォルトで通信なし） |
| 実行記録 | 実行ログ（保存期間あり） | ノード出力の保持 | 段階・値・型・成果物を全記録し、プロジェクトと一緒に移動可能 |
| 保存形式 | DB（JSON エクスポート可） | フォルダ（XML など） | 人が読めるテキストのフォルダ（計算定義と配置を分離） |
| AI の役割 | ワークフロー内で LLM を呼ぶ | 操作の補助 | Draft から型・環境・コードを生成し、実行して検証 |

## n8n・KNIME の方が向いている場面

Tsugumi はあらゆる用途を置き換える万能ツールではありません。次のような場面では、n8n や KNIME を選ぶ方が適しています。

- **外部サービスや SaaS との連携が中心のとき**（Slack への通知、フォーム回答の CRM 登録、Webhook トリガーなど）。Tsugumi の Card はデフォルトでネットワークから隔離されており、SaaS 連携用のコネクタもありません。これは n8n の領域です。
- **コードを書かずに GUI だけでデータ分析を完結させたいとき**。KNIME が備える数千種類の専用ノード（結合・集計・統計検定・機械学習・可視化）に相当するものは Tsugumi にはありません。Tsugumi はあくまで「コードを書く（あるいは AI と一緒にコードを作って読み直す）人」のためのワークベンチです。
- **サーバーで 24 時間常時稼働させたい・ブラウザだけでチーム共有したいとき**。n8n はセルフホスト可能なサーバーとして、KNIME は KNIME Hub / Server として運用できますが、現在の Tsugumi は Apple silicon Mac 向けのデスクトップアプリです（Web UI は将来の構想段階）。
- **Windows や Linux デスクトップで使いたいとき**。Tsugumi は macOS の `Virtualization.framework` と SwiftUI を基盤としているため、macOS 専用です。

裏を返せば、**「自分や AI が書いた計算・解析コードを、環境ごと厳密に固定し、型と記録を残しながら、安全に何度でも回して確かめたい」**という場面において、Tsugumi は他にない強力なワークベンチになることを目指しています。
