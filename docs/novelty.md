# なぜ今、設計・実装・検証を同じ Workflow にするのか

**人間が描く仕様、AI が編集する対象、実際に動く処理を、同じ構造にする。**
Tsugumi の独自性は、この関係を Draft・Card・型・実行環境・版管理まで一貫させたことにあります。

AI が進めた解析を人間が理解し、次の条件を試すには、意図とコードと結果を結びつける必要があります。
Tsugumi では、その結びつきを Workflow として扱います。処理を示す図が実装の対象となり、実行後には結果を確かめ、変更する場所にもなります。

## 描いた仕様が、実装と検証の場所になる

たとえば、観測データを読み、背景ノイズを推定し、モデルに当てはめ、結果を描画する解析を考えます。
最初は各処理を Draft として置き、仮の入出力をつなぎます。どの処理に何を渡すかを、コードを書く前に共有できます。

Agent は説明と接続を読み、Card のコード、出力型、実行環境を作ります。出力型から下流の入力型が導出され、つながる処理の間で契約が揃います。
実行後に背景の推定方法が気になれば、その Card を開いて変更し、保存された入力で試せます。調整ができたら、全体を通して結果を確かめます。

**「ここを変えたい」の「ここ」が、仕様・コード・実行を通じて同じ場所を指す。**
そのため、解析を理解してから変更箇所を探し直すまでの距離を短くできます。

大きな処理は子 Workflow にまとめ、普段は一つの Card として扱えます。必要なときは内部へ降り、より細かい単位で確かめられます。
処理が増えても、人間が考えたい粒度で見渡せるようにする設計です。

## AI が、検証しやすい構造を作る手間を引き受ける

環境の固定、入出力の型定義、処理の分割には、検証しやすさを支える役割があります。
同時に、それらを人間が毎回手で整えるなら、短い試行にも準備の負担がかかります。

Tsugumi の Agent は、Draft に書かれた目的と前後の接続から、その準備を含めて実装できます。
`default.nix` に環境を定義し、`_outputs.fbs` に出力型を書き、C++ / Python / bash の処理を作って、実際に動かしながら修正します。
人間がすべての定義を書き始めなくても、型と環境を備えた部品を組み立てていけます。

**AI に実装を任せられるからこそ、人間が確かめやすい構造を、解析の初めから用意できる。**
これが、今 Tsugumi をこの形で作る理由です。人間は処理の目的と関係を示し、生成された実装と結果を吟味して、次の問いを立てます。

Agent と UI は共通の core の操作・検証の仕組みを使います。AI が保存した Card は通常のプロジェクトファイルとして残り、人間も開いて編集できます。できあがった Workflow の実行に LLM は必要ありません。

## 型と環境が、試行の単位を支える

Card を独立して確かめるには、何を受け取り、どの環境で動き、何を返すのかを明らかにする必要があります。

| 仕組み | 明らかにするもの | 試行の中でできること |
| --- | --- | --- |
| 型付きポート | 前後の処理が受け渡すデータの構造 | 接続の型を実行前に検査し、下流の入力型を導出する |
| Card ごとの Nix 定義 | コードのビルドと実行に使う依存関係 | 環境の定義を版とともに保持し、利用できる Nix の出力を再利用する |
| Card と子 Workflow | 変更して確かめる処理の範囲 | 全体を見渡し、必要な処理の内部へ降りる |
| 保存入力と実行履歴 | 次の試行に使う入力と、実行時の記録 | 一部を修正して試し直し、ログや結果を確認する |

たとえば、重いシミュレーションを seed や条件を明示した Nix のビルドとして定義しておけば、その出力を下流の解析に渡せます。下流だけを変更し、シミュレーションの定義と依存関係が変わらず、出力が Nix store に残っていれば、重い計算を繰り返す必要はありません。

runtime ではストリームや状態を持つ処理も扱えます。Nix で環境や計算を固定することと、到着順や保持状態を含むすべての実行結果を決定的にすることは区別しています。どの条件を固定するかは、解析の性質に応じて設計します。

構成の詳細は[主要機能](features.md)、再現性の考え方は [Q&A](QA.md)を参照してください。

## 一つの結果から、別の仮説へ進める

研究では、うまくいった結果の先にも問いが続きます。
条件を変える。別のモデルを試す。以前は採用しなかった方針へ戻る。そのたびに、どの版の処理で何を試したかをたどれることが重要です。

Tsugumi は、コードや Workflow の定義を Git で管理し、実行にその版を関連づけます。
版のツリーから以前の内容へ戻って別の試行を始められ、ログや表示結果は実行履歴から確認できます。
入出力値の履歴を残すかは `recordIO`、成果物を保持するかは `retainArtifact` で選びます。部分再実行用の最新入力は、全呼び出しの入出力履歴とは別に保存します。

**コードを残すこと、結果を読むこと、次の条件を試すことが、一つの研究の流れになる。**
部分実行で処理を調整し、最後は Workflow 全体を通して確かめる。この往復を支えるために、版管理と実行履歴を組み合わせています。

操作と保存の仕組みは[版の管理](Versions.md)、記録と再実行の設計意図は [Q&A](QA.md)にまとめています。

## 既存のアプローチに重ねて、何を一体化するのか

対話しながらコードを試すこと、処理をグラフで表すこと、依存関係や版を管理することは、それぞれ既存のアプローチにある考え方です。
Tsugumi では、それらを次のようにつなぎます。

| アプローチ | Tsugumi でのつなぎ方 |
| --- | --- |
| コードを動かし、結果を見ながら考える | Card の結果からその処理を開き、保存入力で変更を試す |
| 自然言語で AI に実装を依頼する | Draft の説明に接続関係を加え、実装後も同じ Workflow を共有する |
| グラフで処理の関係を表す | 表示された接続を型の導出と実行の規則に反映する |
| 環境・コード・実験の版を管理する | 実行をコードの版に関連づけ、過去の版から次の試行を始める |

**Tsugumi が目指すのは、人と AI が同じ構造を使って設計し、動かし、考え続けられる研究環境です。**
その構造があることで、研究者は AI の進めた試行に立ち戻り、自分の疑問を具体的な変更として試せます。
研究を出発点に、この関係を学習・開発・引き継ぎへ広げる構想は [Vision.md](Vision.md)、制作の背景は [Philosophy.md](Philosophy.md)を参照してください。
