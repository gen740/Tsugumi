# Tsugumi は n8n や KNIME と何が違うのか

n8n も KNIME も Tsugumi も、「箱（ノード / Card）を線でつないで処理を組み立てる」という見た目は同じです。
しかし、目指しているものは違います。

- **n8n** は SaaS や API をつなぐ**業務自動化**のツールです。Webhook やスケジュールで起動し、Slack・Google Sheets・CRM などの数百の連携ノードでデータを運ぶことが得意です。
- **KNIME** は**データ分析**のためのプラットフォームです。表（data table）を中心に、読み込み・前処理・統計・機械学習・レポートの豊富なノードを GUI で組み合わせることが得意です。
- **Tsugumi** は、**自分で書いたコード（C++ / Python / bash）を、環境ごと固定して、何度でも同じ結果が出る形で実行し、すべてを記録する**ためのツールです。計算・シミュレーション・データ処理のパイプラインを「再現できる実験」として扱うことを目指しています。

以下では、Tsugumi が強い点を具体的に説明します。最後に、n8n・KNIME の方が向いている場面も正直に書きます。

## 1. 環境まで含めて再現できる（Nix）

n8n の Code ノードや KNIME の Python ノードは、**そのマシンに入っている** Node.js / Python / ライブラリで動きます。KNIME は conda 環境を指定できますが、環境の中身（ライブラリのバージョンやネイティブ依存）はマシンごとに解決されます。半年後に別の Mac で開くと、ライブラリの版が変わって結果が変わる、ということが起こりえます。

Tsugumi では **Card ごとに `default.nix` で実行環境を宣言**し、nixpkgs のリビジョンとハッシュまで固定します。

```nix
{ pkgs, inputs, params }: {
  run = inputs.tsugumi.cppCard { sdk = inputs.tsugumi.sdk { languages = [ "cpp" ]; }; src = ./src; };
}
```

- コンパイラ・インタプリタ・ライブラリのバージョンはすべて Nix のハッシュで決まります。同じ定義なら、どの Mac でも同じバイナリになります。
- Card ごとに環境が独立しているので、「この Card は古い numpy、あの Card は新しい numpy」も衝突しません。
- 評価は restricted eval・IFD 禁止で、こっそり外部のファイルやネットワークに依存する定義は書けません。
- 独自のキャッシュではなく Nix の derivation そのものでビルドの要否を判定するため、「キャッシュが古くて結果が違う」が起きません。

**「同じ入力・同じ定義なら同じ結果」を、ツールの仕組みとして保証しにいっている**点が、Tsugumi の一番の違いです。

## 2. 型のあるポート

n8n はノード間を JSON（items の配列）で受け渡し、KNIME は列の型を持つ表を受け渡します。どちらも柔軟ですが、「このポートには何が来るか」は実行してみるまで分からないことが多くあります。

Tsugumi のポートは **FlatBuffers のスキーマで型が決まっています**。

- 出力の型を `_outputs.fbs` で宣言すると、下流の入力型は自動で導出されます。merge は自動で union 型になります。
- 接続時に構造的互換性を検査するので、型の合わない配線は実行前に分かります。
- C++ では `input.number.value` のようにポート名がそのまま型付きの member になります。JSON のキーを文字列で引いて間違える、ということがありません。
- 64 bit 整数・enum・struct・union・ファイル・ディレクトリが、C++ / Python / bash の間で欠落なく受け渡せます（JSON 経由で 64 bit 整数が丸まる、といった問題がない）。

## 3. 本物のプログラムを速く動かせる

n8n の Code ノードは JavaScript / Python の短いスクリプト向けで、KNIME の重い処理は Java のノードか外部の Python / R 連携が中心です。**C++ で書いた計算をそのままノードにする**のはどちらも得意ではありません。

Tsugumi は C++ を第一級の言語として扱います。

- C++ の Card は共有ライブラリ（`lib/main.so`）としてビルドされ、worker がメモリに読み込んで直接呼び出します。プロセス起動もシリアライズの往復もありません。
- worker は実行をまたいで常駐し、状態を保てます。次の worker を先に起動しておくこともできます。
- 実測で、C++ Card の実行段階は平均 0.26 ms、Collatz デモの 1344 回の呼び出しが 0.92〜1.0 秒です（共通 VM 上、2 回目以降。[開発資料の計測](Development.md)）。
- Python・bash も同じ契約で混在でき、C++ と Python の独立実装の結果が一致するかを 1 つのグラフで確かめる、といった使い方ができます（`collatz` デモ）。

## 4. 制御フローを持つグラフ

n8n には IF / Switch / Merge / Loop があり、KNIME にもループや分岐のノードがあります。Tsugumi はこれらを**スケジューラーの意味論として厳密に定義**している点が違います。

- `all`（全入力が揃ったら 1 値ずつ）と `any`（到着順）の待ち方、有界 queue と背圧。
- branch の選ばれなかった側は `skipped`、未実装や失敗に依存する部分は理由付きで `blocked`。独立した部分は止まらずに進みます。
- feedback loop は `maxRuns` で有限に限定され、無限ループになりません。
- Card in Card（子 Workflow）は外から普通の Card として接続・実行でき、単体でも再実行できます。
- さらに Nix の定義から「どの経路で来ても必ず先に実行される上流 Card」の定義を参照でき、この判定は分岐・合流・ループ・入れ子を考慮した静的解析で行います。

## 5. すべてを記録し、後から確かめられる

n8n は実行履歴（execution）を残しますが、保存期間や容量の設定次第で消え、基本は「最後にどう動いたか」の確認用です。KNIME はノードの出力を workflow に保存できますが、過去の実行の比較は別の仕組みが必要です。

Tsugumi は**実行そのものを記録の対象**にしています。

- 呼び出しごとに、どの段階（評価・ビルド・実行・保存）を何ミリ秒で通り、キャッシュを使ったか、どの出力ポートに値を送ったかを記録します。
- 値は FlatBuffers のバイト列のまま、その時点の型（スキーマ）と一緒に保存されるので、後から Card の型を変えても過去の値を正しく読めます。
- 履歴はプロジェクトの `.tsugumi/runs.sqlite` にも書き出され、プロジェクトをコピーしたり別の Mac に移したりしても一緒に移ります。
- 成果物は改ざんを検出できます。
- 「前回の入力でこの Card だけ再実行」ができるので、途中の Card を直して下流だけやり直す、といった実験の進め方に向いています。

## 6. Card ごとの強い隔離

n8n のノードは基本的に n8n 本体と同じプロセス・同じ権限で動き、Code ノードはサーバーの環境にアクセスできます。KNIME のノードもデスクトップアプリと同じ権限で動きます。

Tsugumi の Card は、**Mac から隔離した Linux VM の中で、さらに bubblewrap の sandbox に入れて**実行します（詳細は [security.md](security.md)）。

- Card は既定でネットワークも capability も持たず、見えるのは `/nix/store`（読み取り専用）と自分の入力・作業領域だけです。外部との通信や Mac のフォルダへのアクセスは、Card 定義（`network`・`hostFolders`）で許可した Card だけです（Experimental）。
- プロジェクトごとに uid・名前空間・cgroup が分かれ、あるプロジェクトの Card が別のプロジェクトを覗くことはできません。
- Mac 側から VM に見せるのは、開いているプロジェクトのフォルダと、Card 定義やチャットで指定されたフォルダだけです。

他人が書いた Card や、AI が生成した Card を「とりあえず動かしてみる」ことが、Mac 本体を危険にさらさずにできます。

## 7. ファイルとしての Workflow

n8n の workflow はデータベースに保存され、JSON でのエクスポートはできますが、正本はサーバーの中です。KNIME の workflow はフォルダですが、中身は XML と内部形式で、差分を読んで理解するのは困難です。

Tsugumi のプロジェクトは**普通のフォルダ**です。

- `tsugumi.json`・`definitions/<Card>/_card.json`・`default.nix`・`src/*.cc`・`src/*.py`・`_outputs.fbs`・`layout.json` と、すべて人が読めるテキストです。
- 計算の定義（Card・配線）と見た目（配置・付箋・グループ）はファイルが分かれているので、Git の差分で「計算が変わったのか、見た目だけか」が分かります。
- 保存は journal 付きのトランザクションで、途中で落ちても全件成功か全件未適用のどちらかです。UI と Agent が同時に編集しても、競合は検出され上書きされません。

## 8. AI が「部品」を作る

n8n には AI Agent ノードがあり、KNIME にも AI アシスタントがありますが、主に「ワークフローの中で LLM を呼ぶ」か「ノードの使い方を助ける」ものです。

Tsugumi の Agent は、**グラフの設計とコードの実装を分担する**ための仕組みです。

- 人は Canvas に **Draft**（概要・処理内容・制約・完了条件・仮の入出力）を置いて先に配線し、全体の形を決めます。
- 「Card を生成」で Agent が Draft を読み、型・Nix 定義・ソースを 1 トランザクションで保存し、実際に実行して検証します。失敗や取消では何も保存されません。
- Agent の tool は RPC の契約（FlatBuffers スキーマ）から自動生成されるので、UI と同じ操作を同じ検査付きで行います。UI の画面操作を真似るわけではありません。
- 生成されたコードも §6 の sandbox で動くので、AI が書いたコードを安全に試せます。
- 通常の計算に LLM は不要です。Agent を使わなくても、すべての操作は UI から行えます。

## 9. まとめ

| 観点 | n8n | KNIME | Tsugumi |
| --- | --- | --- | --- |
| 主な用途 | SaaS / API 連携の業務自動化 | データ分析・機械学習 | 自作コードの再現可能な計算パイプライン |
| 実行環境の固定 | マシンの Node.js / Python | マシンの Java / conda | Card ごとに Nix で固定（ハッシュ単位） |
| ノード間のデータ | JSON の items | 型付きの表 | FlatBuffers スキーマの型付き値 |
| C++ のコード | 不可（JS / Python） | 限定的 | 第一級（共有ライブラリを直接呼ぶ） |
| 実行の隔離 | 本体と同じプロセス・権限 | 本体と同じ権限 | VM + bubblewrap、既定でネットワークなし |
| 実行記録 | 実行ログ（保存期間あり） | ノードの出力の保存 | 段階・値・型・成果物を全記録、プロジェクトと一緒に移る |
| 保存形式 | DB（JSON エクスポート可） | フォルダ（XML など） | 人が読めるテキストのフォルダ、計算と見た目を分離 |
| AI の役割 | ワークフロー内で LLM を呼ぶ | 操作の補助 | Draft から型・環境・コードを生成し検証 |

## n8n・KNIME の方が向いている場面

Tsugumi は万能ではありません。次のような用途には n8n や KNIME を選ぶべきです。

- **外部サービスとの連携が中心**（Slack に通知、フォームの内容を CRM に登録、Webhook で起動など）。Tsugumi の Card は既定でネットワークにアクセスできず（Card ごとの許可は Experimental）、連携ノードもありません。これは n8n の領域です。
- **コードを書かずに分析したい**。KNIME の数千のノード（結合・集計・統計・機械学習・可視化）に相当するものは Tsugumi にはありません。Tsugumi は「コードを書く人」のためのツールです。
- **サーバーで常時動かしたい・チームで共有したい**。n8n はセルフホストのサーバーとして、KNIME は KNIME Hub / Server として運用できます。Tsugumi は現在 Apple silicon Mac のデスクトップアプリだけです（Web UI は将来の予定）。
- **Windows / Linux で使いたい**。Tsugumi は macOS 専用です。

逆に言えば、**「自分で書いた計算を、環境ごと固定して、型と記録付きで、安全に何度でも回したい」**という場面では、Tsugumi はこの 2 つのどちらよりも強い道具になることを目指しています。
